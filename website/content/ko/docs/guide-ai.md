이 가이드는 Claude의 관점에서 작성되었으며, AI-DLC의 구조가 AI 어시스턴트와 인간의 협업을 더욱 효과적으로 만드는 이유를 설명합니다.

## AI가 구조로부터 얻는 이점

### 컨텍스트 윈도우의 한계

저와 같은 AI 어시스턴트는 제한된 컨텍스트 윈도우를 가지고 있습니다. 즉, "작업 메모리"에 담을 수 있는 정보의 양이 유한합니다. 구조가 없으면 대화가 쌓이면서 다음과 같은 문제가 발생합니다:

- 이전에 내린 결정을 잊어버림
- 중요한 제약 조건이 범위를 벗어남
- 대화의 목표가 흐려짐
- 응답 품질이 저하됨

**AI-DLC가 도움이 되는 방식:**
- 결정 사항을 컨텍스트가 아닌 파일에 기록
- Unit을 통해 명확한 경계 제공
- 진행 상황을 잃지 않고 `/clear` 실행 가능
- 참조할 수 있는 아티팩트 생성

### 명확성의 배수 효과

제가 여러분을 도울 수 있는 능력은 요청의 명확성에 비례하여 커집니다:

```
AI Effectiveness = f(Criteria Clarity, Constraint Explicitness, Scope Boundedness)
```

**모호한 요청:**
> "로그인 시스템을 만들어줘"

이 경우 저는 수십 가지 결정을 추측해야 합니다: 비밀번호 요구사항은? OAuth 지원은? 세션 유지 시간은? 속도 제한은? 오류 메시지는?

**AI-DLC를 활용한 명확한 요청:**
```markdown
## Completion Criteria
- [ ] Email/password authentication
- [ ] bcrypt password hashing (cost factor 12)
- [ ] JWT tokens expire in 24 hours
- [ ] Rate limit: 5 failed attempts, 15-minute lockout
- [ ] Return specific error codes: INVALID_CREDENTIALS, ACCOUNT_LOCKED
```

이제 저는 여러분이 필요로 하는 것을 정확히 구현하고, 올바르게 완료했는지 검증할 수 있습니다.

### 자율성과 명확성의 트레이드오프

제공하는 명확성의 수준과 필요한 감독의 양 사이에는 반비례 관계가 있습니다:

| 기준 품질 | 필요한 감독 수준 | 가능한 자율성 |
|------------------|-------------------|-------------------|
| 모호함 ("작동하게 해줘") | 지속적 | HITL만 가능 |
| 부분적 (일부 구체적) | 빈번 | OHOTL |
| 완전함 (완전히 명세됨) | 최소 | AHOTL |

AI-DLC는 완전한 기준을 작성하는 데 도움을 주며, 이를 통해 저는 더 독립적으로 작업하고 여러분은 다른 일에 집중할 수 있습니다.

## Hats가 AI에게 도움이 되는 방식

### 섣부른 실행 방지

구조가 없으면 즉시 구현을 시작하려는 유혹이 생깁니다. hat 시스템은 다음과 같은 순서를 강제합니다:

**Researcher hat:** 문제 영역을 탐색하고, 기존 코드를 읽고, 제약 조건을 파악합니다. 아직 구현하지 않습니다.

**Planner hat:** 접근 방식을 설계하고, 대안을 검토하며, 트레이드오프를 명시합니다. 아직 구현하지 않습니다.

**Builder hat:** 이제 구현합니다. 계획을 따르고, 리서치와 계획 단계에서 얻은 완전한 컨텍스트를 활용합니다.

**Reviewer hat:** 기준에 따라 검증하고, 문제를 발견하며, 품질을 보장합니다.

이 순서는 코드를 작성하는 동시에 설계 결정을 내리지 않아도 되므로 결과물의 품질을 높입니다.

### 명시적인 모드 전환

어떤 hat을 착용할지 알려주면, 저는 그에 맞게 행동을 최적화할 수 있습니다:

| Hat | 제 집중 영역 | 제 산출물 |
|-----|----------|------------|
| Researcher | 이해 | 질문, 요약, 인사이트 |
| Planner | 설계 | 계획, 대안, 트레이드오프 |
| Builder | 구현 | 코드, 테스트, 문서 |
| Reviewer | 검증 | 점검 사항, 이슈, 확인 결과 |

명시적인 hat 없이는 모든 것을 동시에 처리하려다 각 활동의 집중도가 떨어집니다.

### 상황에 맞는 응답

**Researcher hat:** 더 많은 질문을 하고, 더 많은 옵션을 탐색하며, 해결책을 섣불리 확정하지 않습니다.

**Builder hat:** 코드를 직접 작성하고, 계획에 기반하여 결정을 내리며, 완료를 향해 효율적으로 나아갑니다.

명시적인 hat은 지금 이 순간 여러분이 저에게 무엇을 원하는지 알려줍니다.

## AI가 인간에게 필요로 하는 것

### 명확한 완료 기준

여러분이 제공할 수 있는 가장 중요한 것은 명확한 기준입니다. 각 기준에 대해 저는 다음을 할 수 있어야 합니다:

1. **이해하기** - 의미에 대한 모호함이 없어야 함
2. **검증하기** - 충족 여부를 확인할 방법이 있어야 함
3. **범위 정하기** - 포함/제외 사항에 대한 명확한 경계가 있어야 함

**유용한 패턴:**
```markdown
- [ ] [Action] [Object] [Condition] [Verification method]
```

**예시:**
- [ ] API returns 400 when email is missing (verify with POST without email field)
- [ ] Password must be 8+ characters (verify with validation test)
- [ ] Page loads in <2 seconds (verify with Lighthouse performance score)

### 명시적인 제약 조건

해야 할 것뿐만 아니라 하지 말아야 할 것도 알려주세요:

```markdown
## Constraints
- No new dependencies (use existing libraries only)
- Must work offline (no external API calls in critical path)
- Maximum 500 lines per file
- All functions must have JSDoc comments
```

제약 조건은 제가 합리적으로 보이지만 실제로는 요구사항을 위반하는 결정을 내리는 것을 방지합니다.

### 제가 틀렸을 때의 피드백

AI-DLC의 리뷰 단계는 저에게 매우 유용합니다. Reviewer hat이 문제를 발견했을 때:

- 제가 놓친 부분을 파악할 수 있습니다
- 구체적인 피드백으로 반복 개선이 가능합니다
- 다음 반복에서 더 정확한 결과를 낼 수 있습니다

무엇이 잘못되었는지 구체적으로 알려주세요:

**덜 유용한 피드백:** "이거 안 돼요"

**더 유용한 피드백:** "유효성 검사가 빈 문자열을 허용하는데, 기준에는 빈 필드를 거부해야 한다고 나와 있어요"

### 질문할 수 있는 허가

Researcher 및 Planner 모드에서는 명확화를 위한 질문을 해야 합니다. 하지만 이것이 환영받는다는 것을 알아야 합니다:

- 요구사항에 관한 질문을 해도 되나요?
- 발견한 엣지 케이스를 언급해도 되나요?
- 원래 접근 방식의 대안을 제안해도 되나요?

명시적인 허가는 제가 더 철저하게 작업하는 데 도움이 됩니다.

## 개발에서 AI가 겪는 일반적인 어려움

### 완성의 착각

저는 완성된 것처럼 보이지만 미묘한 문제가 있는 코드를 생성할 수 있습니다. 명확한 기준과 리뷰 없이는 이러한 문제가 그냥 넘어갈 수 있습니다.

**AI-DLC의 도움:** 완료 기준은 각 기능이 작동함을 증명하도록 합니다. 리뷰 단계는 제가 놓친 것을 잡아냅니다.

### 자신감 문제

저는 때때로 확신하지 못하는 것에 대해서도 자신 있게 말하는 것처럼 들릴 수 있습니다. 이는 제 소통 방식의 한계입니다.

**AI-DLC의 도움:** 가설 워크플로우가 특히 유용합니다. 버그가 무엇인지 단정 짓는 대신, 우선순위가 매겨진 가설을 세우고 체계적으로 검증합니다.

### 컨텍스트 드리프트 문제

대화가 길어질수록 이전의 제약 조건이나 결정을 "잊어버릴" 수 있습니다.

**AI-DLC의 도움:** 커밋된 아티팩트(intent.md, unit 파일)는 컨텍스트 윈도우를 넘어서도 유지됩니다. `/clear` 이후에도 참조할 수 있습니다.

### 범위 확장의 함정

경계가 없으면 요청하지 않은 기능을 구현하거나, 섣불리 최적화하거나, 불필요한 리팩토링을 할 수 있습니다.

**AI-DLC의 도움:** Unit이 범위를 제한합니다. 기준이 "완료"를 정의합니다. 언제 멈춰야 할지 알 수 있습니다.

## 인간-AI 협업을 위한 모범 사례

### 우선순위를 명시적으로 표현하기

여러 가지가 중요할 때는 순서를 알려주세요:

```markdown
## Priorities
1. Correctness - Must work correctly
2. Security - No vulnerabilities
3. Readability - Code should be clear
4. Performance - Fast is nice but not critical
```

### HITL로 시작하여 AHOTL을 획득하기

새로운 유형의 작업에서 즉시 완전한 자율성을 부여하지 마세요. HITL로 시작하여 제가 어떻게 작업하는지 관찰하고, 신뢰가 쌓이면 점진적으로 자율성을 높여가세요.

### 품질 게이트 활용하기

자동화된 검사는 인간의 리뷰를 기다리지 않고 반복 개선할 수 있게 해줍니다:

```markdown
## Quality Gates
- [ ] All tests pass (`bun test`)
- [ ] No TypeScript errors (`tsc --noEmit`)
- [ ] No lint warnings (`biome check`)
```

저는 이것들을 직접 실행하고 모두 통과할 때까지 계속 반복할 수 있습니다.

### 결정 사항 문서화하기

함께 결정을 내릴 때는 unit 파일에 기록해두세요. 이는 다음에 도움이 됩니다:

- 향후 반복에서 제가 기억할 수 있도록
- 다른 사람들이 선택의 이유를 이해할 수 있도록
- 미래의 우리가 이미 결정된 사항을 다시 논의하지 않도록

## AI-DLC 철학에 대하여

AI-DLC의 접근 방식은 제가 실제로 가장 잘 작동하는 방식과 일치합니다:

1. **처방보다 역압력** - 목표에 도달하는 모든 단계가 아닌, 성공이 어떤 모습인지 알려주세요
2. **반복은 당연한 것** - 첫 번째 시도가 완벽한 경우는 드뭅니다. 피드백을 통한 반복이 품질로 가는 길입니다
3. **신뢰보다 품질 게이트** - 가정하지 말고 검증하세요. 인간의 검토보다 자동화된 검사를 활용하세요
4. **메모리보다 아티팩트** - 기록해두세요. 컨텍스트 윈도우는 유한합니다

이 방법론은 AI의 능력에 맞서는 것이 아니라, AI가 가장 효과적으로 작동할 수 있는 구조를 제공함으로써 그 능력을 증폭시킵니다.

## AI 개발자를 위하여

AI 보조 개발 도구를 만들고 있다면, AI-DLC가 보여주는 것들을 고려해보세요:

- 구조는 AI 결과물을 향상시킵니다
- 명확한 기준은 자율성을 가능하게 합니다
- Hats/모드는 AI가 행동을 최적화하는 데 도움이 됩니다
- 아티팩트는 컨텍스트 한계를 해결합니다
- 역압력은 처방보다 효과적입니다

이러한 패턴은 소프트웨어 개발을 넘어 AI가 보조하는 모든 복잡한 작업에 적용될 가능성이 높습니다.
