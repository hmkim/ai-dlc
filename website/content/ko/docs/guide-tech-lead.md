이 가이드는 팀에 AI-DLC를 도입할 책임이 있는 기술 리드를 위한 문서입니다. 준비 과정, 롤아웃 전략, 그리고 성공 측정 방법을 다룹니다.

## 팀 도입 준비

### 먼저 개인적인 숙달부터

팀에 AI-DLC를 소개하기 전에, 먼저 본인이 충분히 숙련되어 있어야 합니다:

- [ ] 개인적으로 최소 5개의 Unit 완료
- [ ] 여러 워크플로우 유형 사용 경험
- [ ] 일반적인 실패 패턴 경험
- [ ] 컨벤션에 대한 자신만의 의견 형성
- [ ] 기본적인 질문에 자신 있게 답변 가능

### 첫 번째 프로젝트 선정

모든 작업이 AI-DLC 도입에 동일하게 적합한 것은 아닙니다. 다음 특성을 가진 프로젝트부터 시작하세요:

| 특성 | 도움이 되는 이유 |
|----------------|--------------|
| 시간 압박이 적음 | 학습 곡선을 소화할 여유 확보 |
| 명확한 요구사항 | 좋은 기준 작성이 용이함 |
| 독립적인 범위 | 영향 범위가 제한적 |
| 적절한 규모 | 학습하기에 충분하되 부담스럽지 않음 |
| 기술적 친숙도 | 한 번에 하나씩 새로운 것을 익힘 |

**첫 도입 시 피해야 할 작업:**
- 크리티컬 패스 산출물
- 많은 컨텍스트가 필요한 레거시 시스템
- 광범위한 이해관계자 조율이 필요한 프로젝트
- 고도로 탐색적인 R&D 작업

### 자료 준비

팀 소개 전에:

1. **예시 Intent** - 해당 도메인에 맞는 현실적인 예시 준비
2. **녹화된 데모** - 또는 팀을 위한 라이브 데모 계획
3. **FAQ 문서** - 예상 질문과 답변 미리 준비
4. **성공 사례** - 본인의 긍정적인 경험 공유

## AI-DLC 롤아웃

### 챔피언 모델 (권장)

가장 효과적인 롤아웃 패턴:

```
1단계: 챔피언이 독립적으로 작업 (1~2 스프린트)
    ↓
2단계: 챔피언이 팀에 시연 (1회 세션)
    ↓
3단계: 페어 프로그래밍 - 챔피언 + 각 팀원 (각 1개 Unit)
    ↓
4단계: 챔피언이 지원 가능한 상태에서 독립 작업 (2~3 스프린트)
    ↓
5단계: 팀이 독립적으로 운영
```

**이 방식이 효과적인 이유:**
- 챔피언이 팀에 영향을 미치기 전에 문제를 먼저 경험
- 시연을 통해 공통된 맥락 형성
- 페어링으로 학습 가속화
- 점진적인 독립을 통해 자신감 구축

### 병렬 모델 (대안)

경험 있는 개발자가 여러 명인 팀을 위한 방식:

```
1단계: 자원자 2~3명이 독립적으로 학습 (1~2 스프린트)
    ↓
2단계: 자원자들이 학습 내용 공유 (1회 세션)
    ↓
3단계: 각 자원자가 팀원 1~2명 지원
    ↓
4단계: 전체 팀 도입
```

**이 방식이 효과적인 이유:**
- 방법론에 대한 다양한 관점 확보
- 롤아웃에 대한 공동 책임감 형성
- 규모가 큰 팀에서 더 빠른 전파 가능

### 팀 소개 세션

60분 소개 세션 구성:

| 시간 | 활동 |
|------|----------|
| 0~10분 | AI-DLC 소개: 문제 정의 및 이점 |
| 10~30분 | 라이브 데모: 소규모 Unit 처음부터 끝까지 완료 |
| 30~45분 | Q&A: 우려 사항 및 질문 처리 |
| 45~55분 | 첫 단계: 시작 방법 안내 |
| 55~60분 | 다짐: 누가 먼저 시도할 것인가? |

**핵심 전달 사항:**
- AI-DLC는 제약이 아닌 구조에 관한 것
- hat 전환은 처음에는 어색하지만 곧 자연스러워짐
- 목표는 품질 향상이며, 속도는 그 뒤를 따름
- 회의적인 시각도 괜찮음 - 공정하게 시도해 보는 것이 중요

### 일반적인 우려 사항 대응

| 우려 사항 | 대응 |
|---------|----------|
| "속도가 느려질 것 같아요" | "처음에는 그럴 수 있습니다. 하지만 품질 향상으로 재작업이 줄어듭니다. 판단하기 전에 5개 Unit을 해보세요." |
| "무엇을 만들어야 할지 이미 알고 있어요" | "리서치를 하다 보면 예상치 못한 발견이 있습니다. 5분 타임박스 리서치를 한번 해보세요." |
| "오버헤드가 너무 많아요" | "대부분의 오버헤드는 학습 곡선입니다. 숙달되면 크게 줄어듭니다." |
| "AI가 실수를 할 거예요" | "맞습니다. 그래서 검토 단계와 명확한 기준이 있는 것입니다. 시스템이 실수를 잡아냅니다." |
| "마음에 들지 않으면 어떡하죠?" | "타당한 우려입니다. 결정하기 전에 3~5개 Unit을 진지하게 시도해 보세요. 맞지 않는다면 함께 논의하겠습니다." |

## 팀 컨벤션 수립

### 표준화할 항목

팀이 합의해야 할 사항:

**파일 구성:**
```
.ai-dlc/
  intent.md                    # 메인 Intent
  unit-01-description.md       # 순서 + 설명
  unit-02-description.md
```

**커밋 메시지:**
```
feat(auth): complete unit-01-login-api

AI-DLC unit: unit-01-login-api
Status: complete
Criteria met: 5/5
```

**PR 형식:**
```markdown
## Intent
[intent.md 링크 또는 관련 섹션 복사]

## Units Completed
- unit-01-x: [간략한 설명]
- unit-02-y: [간략한 설명]

## Completion Criteria
[unit 파일에서 복사하거나 링크]
```

**Pass 설정:**

기본적으로 크로스 펑셔널 반복을 원하는 팀은 `.ai-dlc/settings.yml`에서 `default_passes`를 설정하여 새 Intent가 자동으로 디자인, 프로덕트, 개발 Pass를 포함하도록 할 수 있습니다:

```yaml
# .ai-dlc/settings.yml
default_passes: [design, product, dev]
```

이 설정이 없으면 Intent는 기본적으로 단일 dev Pass로 설정됩니다. Pass의 작동 방식은 [Passes](/docs/concepts/#pass)를 참고하세요.

**디자인 프로바이더 설정:**

AI-DLC는 6가지 디자인 프로바이더(Canva, Figma, OpenPencil, Pencil, Penpot, Excalidraw)를 지원합니다. MCP 도구에서 자동 감지하려면 `type: auto`로 설정하거나, 특정 프로바이더를 고정할 수 있습니다:

```yaml
# .ai-dlc/settings.yml
providers:
  design:
    type: figma
    config:
      project_id: "PROJ-123"
      team_id: "TEAM-456"
    instructions: |
      - Only reference designs marked "Ready for Dev"
```

각 프로바이더마다 지원 기능이 다릅니다. 전체 기능 매트릭스와 프로바이더별 설정 옵션은 [디자인 프로바이더 가이드](/docs/guide-design-providers/)를 참고하세요.

### 표준화하지 말아야 할 항목

다음 항목은 개인의 유연성을 허용하세요:
- hat 전환 타이밍
- 리서치 노트의 세부 수준
- 각 hat 내에서의 작업 스타일
- 다양한 워크플로우에 대한 선호도

### 컨벤션 문서화

팀 AI-DLC 가이드를 작성하세요:

```markdown
# 팀 AI-DLC 컨벤션

## 파일 구조
[팀의 컨벤션]

## 워크플로우 선택
- 기본: 대부분의 기능 작업
- TDD: 버그 수정, 명확하게 명세된 동작
- 적대적: 보안에 민감한 기능

## 커밋 전략
[팀의 접근 방식]

## 리뷰 통합
[AI-DLC와 PR 리뷰의 통합 방식]
```

## 기존 프로세스와의 통합

### 스프린트 플래닝

**AI-DLC 도입 전:**
> "이 기능은 3 스토리 포인트가 걸릴 것입니다"

**AI-DLC 도입 후:**
> "이 기능은 4개의 Unit으로 나뉩니다. 유사한 과거 작업을 기준으로 스프린트당 2~3개의 Unit을 완료할 수 있습니다."

Unit 기반 추정의 이점:
- 스토리 포인트보다 세분화된 단위
- 완료 기준으로 범위가 명확해짐
- Unit DAG에서 의존성이 명시적으로 드러남

### 데일리 스탠드업

팀원들이 다음을 보고할 수 있습니다:
- 현재 Unit과 hat
- 문서화된 블로커
- 예상 Unit 완료 시점

예시:
> "인증 Intent의 unit-02 작업 중이며, Builder hat을 쓰고 있습니다. 블로커 없음. 오늘 완료하고 내일 unit-03으로 넘어갈 예정입니다."

### 풀 리퀘스트 리뷰

AI-DLC를 사용하면 PR 리뷰가 더 쉬워집니다:

1. **맥락이 명확함** - Intent와 Unit 파일이 "왜"를 설명
2. **범위가 한정됨** - 리뷰어가 무엇을 기대해야 할지 파악 가능
3. **기준이 문서화됨** - 리뷰를 위한 체크리스트 제공
4. **Review hat 착용 완료** - AI가 이미 1차 리뷰 수행

리뷰어는 다음에 집중할 수 있습니다:
- 구현이 기준을 충족했는가?
- 기준이 놓친 케이스가 있는가?
- AI가 놓친 코드 품질 문제가 있는가?

### 회고

AI-DLC 관련 논의를 추가하세요:
- 어떤 워크플로우가 잘 작동했는가?
- 조정이 필요한 컨벤션이 있는가?
- 관찰된 품질 향상이 있는가?
- 해결해야 할 불편한 점이 있는가?

## 성공 측정

### 추적할 지표

**도입 지표:**
| 지표 | 측정 방법 | 목표 |
|--------|----------------|--------|
| 팀 참여율 | Unit 파일을 생성하는 인원 | 100% |
| 완료된 Unit 수 | 완료된 Unit 집계 | 증가 추세 |
| 워크플로우 다양성 | 사용된 워크플로우 종류 | 모두 적절히 활용 |

**품질 지표:**
| 지표 | 측정 방법 | 목표 |
|--------|----------------|--------|
| 버그 발생률 | Unit당 버그 수 | 감소 추세 |
| PR 수정 횟수 | 변경을 요구하는 코멘트 수 | 감소 추세 |
| 테스트 커버리지 | 커버리지 리포트 | 증가 추세 |
| 기준 명확성 | 기준 품질 검토 | 개선 추세 |

**효율성 지표:**
| 지표 | 측정 방법 | 목표 |
|--------|----------------|--------|
| Unit 완료율 | 스프린트당 Unit 수 | 안정적이거나 증가 |
| 블록 시간 | Unit이 블록된 상태로 있는 시간 | 감소 추세 |
| 재작업률 | 재오픈이 필요한 Unit 수 | 낮게 유지 |

### 파일럿 운영

규모가 큰 팀의 경우, 통제된 파일럿을 운영하세요:

1. **파일럿 그룹 선정** - 자원자 2~3명
2. **성공 기준 정의** - AI-DLC 도입이 가치 있다고 판단할 기준은 무엇인가?
3. **파일럿 기간 설정** - 4~6 스프린트
4. **데이터 수집** - 위의 지표 추적
5. **피드백 수집** - 참여자 인터뷰
6. **결정** - 확대, 조정, 또는 중단

### 리더십에 보고

AI-DLC 도입 현황을 보고할 때:

**집중할 사항:**
- 품질 향상 (버그, 재작업)
- 개발자 만족도
- 프로세스 가시성
- 구체적인 성공 사례

**피해야 할 사항:**
- 너무 이른 시점에 시간 절감 효과 주장
- 모든 개선을 AI-DLC만의 성과로 귀속
- 자율성 이점 과장

## 어려움 대처

### 회의론자

일부 팀원은 회의적인 시각을 가질 것입니다. 이는 건강한 반응입니다.

**해야 할 것:**
- 그들의 우려를 인정
- 결정하기 전에 3~5개 Unit을 시도해 달라고 요청
- 열정적인 도입자와 페어링
- 구체적인 피드백에 귀 기울이기

**하지 말아야 할 것:**
- 원하지 않는 개발자에게 도입 강요
- 우려를 변화에 대한 저항으로 일축
- 가치를 증명하기 전에 AI-DLC를 의무화

### 과도한 도입자

일부는 모든 것에 AI-DLC를 사용하려 할 것입니다.

**주의해야 할 징후:**
- 사소한 작업(5분짜리 수정)에 AI-DLC 사용
- 모든 소소한 변경에 Intent 생성
- 실제 작업보다 프로세스에 더 많은 시간 소비

**다음 방향으로 안내:**
- 적절한 작업 선택
- 소규모 작업에는 가볍게 활용
- 구조와 실용성의 균형 유지

### 품질이 개선되지 않는 경우

도입 후에도 품질 지표가 개선되지 않는다면:

**조사할 사항:**
- 기준이 잘 작성되고 있는가?
- Review hat이 실제로 착용되고 있는가?
- 품질 게이트가 적용되고 있는가?
- 테스트 커버리지가 충분한가?

**대응 방법:**
- 기준 작성 관행 검토
- 품질 게이트 요건 강화
- 추가 교육 제공
- 리뷰 Unit을 함께 페어링
