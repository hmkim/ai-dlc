이 가이드는 AI-DLC를 사용하는 일상적인 워크플로를 다룹니다. 초기 설정을 완료하고 본격적으로 작업할 준비가 된 상태를 전제로 합니다.

## 일상적인 워크플로

### 세션 시작하기

1. **현재 상태 확인**
   - `.ai-dlc/`에서 활성 Intent 확인
   - 현재 작업 중인 Unit 확인
   - 이전 세션에서 남긴 블로커 검토

2. **컨텍스트 로드**
   - 기존 작업을 이어가는 경우 `/ai-dlc:execute` 실행
   - 새 작업을 시작하는 경우 `/ai-dlc:elaborate` 실행

3. **현재 hat 선언**
   - 어떤 hat을 쓰고 있는지 명시적으로 밝히기
   - 이를 통해 본인과 Claude 모두 집중력을 유지할 수 있음

### 세션 진행 중

**자신의 hat에 머무르세요.** 생산성을 가장 크게 떨어뜨리는 요인은 무의식적인 컨텍스트 전환입니다. Builder hat을 쓰고 있다면 대안을 조사하기 시작하지 마세요. Research 모드라면 코딩을 시작하지 마세요.

**프로세스를 신뢰하세요.** Hat 전환은 처음에는 부담스럽게 느껴집니다. 하지만 몇 개의 Unit을 거치고 나면 자연스러워지고 오히려 작업 속도가 빨라집니다.

**진행하면서 기록하세요.** 새로 알게 된 내용에 따라 완료 기준을 업데이트하세요. 블로커가 생기면 바로 추가하세요. Unit 파일에 결정 사항을 문서화하세요.

### 세션 종료하기

1. **현재 상태 커밋**
   - `.ai-dlc/` 파일이 현재 상태를 반영하는지 확인
   - 진행 중인 작업을 설명적인 메시지와 함께 커밋

2. **중단 지점 기록**
   - Unit 상태 업데이트 (진행 중, 블로킹됨 등)
   - 재개에 필요한 컨텍스트 추가

3. **필요 시 초기화**
   - `/clear`는 컨텍스트를 초기화하지만 파일은 유지
   - 컨텍스트가 너무 무거워지거나 혼란스러울 때 사용

## 일반적인 시나리오

### 기존 Intent 이어받기

Unit 중간에 작업을 멈췄거나, 동료로부터 Intent를 인계받은 경우입니다.

```
/ai-dlc:execute
```

이 명령은 Intent와 현재 Unit 상태를 로드합니다. 지금까지 진행된 내용을 검토하세요:

- 전체 목표를 파악하려면 `intent.md` 읽기
- 완료 기준 상태를 확인하려면 Unit 파일 확인
- 문서화된 블로커 확인

그런 다음 작업이 중단된 지점부터 이어가세요.

### 새 작업 시작하기

기존 Intent 없이 새로운 태스크가 생긴 경우입니다.

```
/ai-dlc:elaborate
```

이 명령은 Elaborator 모드로 진입하여 Intent를 협력적으로 정의합니다:

1. 만들고자 하는 것을 설명
2. Claude의 명확화 질문에 답변
3. 제안된 Unit과 기준 검토
4. 구조 승인 또는 수정
5. 실행 전 사양의 모순, 숨겨진 복잡성, 누락된 부분을 검토하는 적대적 리뷰 진행

### 컨텍스트가 무거워질 때

컨텍스트가 무거워지는 징후:
- Claude가 이전 결정을 잊어버림
- 응답이 느려짐
- 제안의 품질이 저하됨

해결 방법:

```
/clear
```

이후 `/ai-dlc:execute`로 커밋된 상태에서 다시 로드하세요. Hat 시스템 덕분에 진행 상황은 컨텍스트가 아닌 파일에 저장됩니다.

### 막혔을 때

블로커에 부딪혔을 때:

1. **문서화** - Unit 파일 또는 `blockers.md`에 추가
2. **분류** - 기술적 문제인가? 요구사항 불명확? 외부 의존성?
3. **행동 결정** - 우회할 수 있는가? 도움이 필요한가? 다른 Unit으로 전환할 것인가?

해결하기 어려운 기술적 문제라면:

```
/researcher
```

Research 모드로 전환하여 조사하세요. 이해가 되면 Builder로 돌아오세요.

요구사항 관련 질문이라면:
- 질문 문서화
- 가정 사항 기록
- 검토 요청 표시
- 가정을 바탕으로 계속 진행

### 여러 Unit이 준비된 경우

블로킹 의존성이 없는 Unit이 여러 개 있을 때는 어떤 순서로든 작업할 수 있습니다. 다음을 고려하세요:

- **가장 작은 것은?** 빠른 성과가 모멘텀을 만듦
- **리스크를 줄이는 것은?** 불확실한 부분을 먼저 해결
- **가장 흥미로운 것은?** 동기 부여도 중요함

### Unit 중간에 리팩토링이 필요할 때

접근 방식을 크게 바꿔야 한다는 것을 깨달은 경우입니다.

**하지 말 것:** 조용히 리팩토링하고 계속 진행

**해야 할 것:**
1. Planner hat으로 전환
2. 변경이 필요한 이유 문서화
3. 계획 업데이트
4. Builder로 복귀
5. 새 계획 실행

나중에 변경 사항을 설명해야 할 때 기록이 도움이 됩니다.

## Hat 전환

### Hat을 전환해야 할 때

| 현재 Hat | 전환 시점 | 전환 대상 |
|-------------|----------------|-------|
| Researcher | 계획을 세울 만큼 충분히 이해했을 때 | Planner |
| Planner | 계획이 완성되고 승인되었을 때 | Builder |
| Builder | 구현이 완료되었을 때 | Reviewer |
| Builder | 이해하지 못하는 부분이 있다는 것을 깨달았을 때 | Researcher |
| Reviewer | 문제가 발견되었을 때 | Builder |
| Reviewer | 모든 기준이 Pass되었을 때 | 다음 Unit |

### 전환을 의도적으로 하기

나쁜 예 (무의식적 전환):
> "이 API가 어떻게 동작하는지 잠깐 확인해보자... 어차피 여기 있으니 구현도 해버리자..."

좋은 예 (의도적 전환):
> "API 계약을 이해하기 위해 Researcher hat으로 전환합니다."
> [리서치]
> "API에 대한 이해를 바탕으로 Builder hat으로 복귀합니다."

### 전환 명령어

```
/researcher   # 리서치 모드 진입
/planner      # 플래닝 모드 진입
/builder      # 빌딩 모드 진입
/reviewer     # 리뷰 모드 진입
```

각 명령어는 적절한 컨텍스트와 마인드셋을 로드합니다.

## 좋은 완료 기준 작성하기

기준의 품질이 Claude가 얼마나 자율적으로 작업할 수 있는지를 결정합니다.

### 검증 테스트

각 기준에 대해 "기계가 이것을 검증할 수 있는가?"라고 자문하세요.

| 기준 | 검증 가능? | 개선된 버전 |
|-----------|-------------|----------------|
| "로그인이 동작함" | 아니오 | "유효한 자격증명으로 POST /api/login 시 유효한 토큰과 함께 200 반환" |
| "성능이 좋음" | 아니오 | "API가 p95 기준 200ms 이내에 응답" |
| "오류 처리" | 아니오 | "필수 필드 누락 시 오류 메시지와 함께 400 반환" |
| "깔끔한 코드" | 아니오 | "ESLint 오류 없음, 모든 함수 50줄 미만" |

### 부정적 케이스 포함하기

정상 동작만 명세하지 마세요:

```markdown
## 완료 기준

### 성공 케이스
- [ ] 유효한 이메일 + 비밀번호 -> 인증 토큰 반환
- [ ] 이후 요청에 토큰 포함 -> 인가됨

### 실패 케이스
- [ ] 이메일 누락 -> 400 "Email required"
- [ ] 잘못된 비밀번호 -> 401 "Invalid credentials"
- [ ] 만료된 토큰 -> 401 "Token expired"

### 엣지 케이스
- [ ] 공백이 포함된 이메일은 트리밍됨
- [ ] 유니코드 문자가 포함된 비밀번호 동작 확인
```

### 품질 게이트

모든 Unit에는 품질 게이트가 포함되어야 합니다:

```markdown
## 품질 게이트
- [ ] 모든 테스트 통과
- [ ] TypeScript 오류 없음
- [ ] 린트 경고 없음
- [ ] 새 코드의 테스트 커버리지 >80%
```

## 생산성 향상 팁

### 유사한 작업 묶기

유사한 Unit이 여러 개 있는 경우(예: CRUD 엔드포인트), 묶어서 처리하세요:

1. 공통 패턴을 한 번만 리서치
2. 플래닝에서 템플릿 접근 방식 수립
3. 순서대로 모두 빌드
4. 그룹으로 리뷰

### 적절한 워크플로 사용하기

| 태스크 유형 | 워크플로 | 이유 |
|-----------|----------|-----|
| 새 기능 | 기본 | 균형 잡힌 사이클 |
| 알려진 버그 | TDD | 테스트로 재현 및 검증 |
| 원인 불명 버그 | 가설 기반 | 체계적인 조사 |
| 보안 기능 | 적대적 | 내장된 공격/방어 사이클 |

### 반복을 받아들이기

AI-DLC는 반복을 전제로 합니다. 첫 번째 시도에서 모든 기준을 충족하는 경우는 드뭅니다. 이는 정상적이며 의도된 설계입니다.

역압 원칙: 성공의 모습을 정의하고, Claude가 그 방법을 찾도록 하고, 모든 기준이 Pass될 때까지 반복하세요.

### Unit을 작게 유지하기

하나의 집중된 세션(2~4시간)을 초과하는 Unit은 너무 큰 것입니다. 분할하세요.

Unit이 너무 크다는 징후:
- 완료 기준이 10개 이상
- 주요 컴포넌트 3개 이상에 영향
- 무엇을 하고 있었는지 계속 잊어버림

## 문제 해결

### "Claude가 계속 엉뚱한 방향으로 가요"

- 기준이 너무 모호할 수 있음
- 일시적으로 HITL 모드로 전환해보기
- 더 구체적인 제약 조건 작성

### "이게 오버헤드처럼 느껴져요"

- 처음 몇 개의 Unit에서는 정상적인 반응
- 판단하기 전에 5개 이상의 Unit을 경험해보기
- 속도보다 품질 향상에 집중

### "답을 이미 아는데 왜 리서치를 해야 하나요?"

- 리서치에서 예상치 못한 발견이 생기는 경우가 많음
- 최소 5분은 투자하기
- 리서치 단계에 시간 제한을 설정할 수 있음

### "리뷰에서 문제가 너무 많이 발견됐어요"

- 좋은 신호입니다! 시스템이 제대로 작동하고 있는 것
- 문제를 수정하고 재리뷰
- 기준이 충분히 명확했는지 검토
