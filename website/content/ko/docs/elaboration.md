구체화는 모든 AI-DLC Intent의 첫 번째 단계입니다. 이 단계에서 여러분과 AI가 협력하여 *무엇을* 만들지, *왜* 중요한지, *완료 여부를 어떻게 판단할지*를 정의합니다. `/ai-dlc:elaborate`를 실행하여 시작하세요.

## 구체화의 결과물

구체화가 끝나면 `.ai-dlc/{intent-slug}/` 디렉터리에 다음과 같은 스펙 파일들이 생성됩니다:

| 파일 | 목적 |
|------|---------|
| `intent.md` | 문제 정의, 솔루션 접근 방식, 도메인 모델, 성공 기준 |
| `unit-01-*.md` | 첫 번째 Unit — 자체 스펙을 갖춘 독립적인 작업 단위 |
| `unit-02-*.md` | 추가 Unit (복잡한 Intent의 경우) |
| `discovery.md` | 기술 탐색 결과 — API 스키마, 코드베이스 패턴, 데이터 소스 |
| `mockups/` | 프론트엔드/디자인 Unit의 와이어프레임 (해당하는 경우) |

이 파일들은 실행 단계(`/ai-dlc:execute`)에서 구현의 기준이 되는 계약서 역할을 합니다.

## 진행 흐름

구체화는 여러 단계로 구성됩니다. 사용자로서 *직접 참여하는* 단계와 자동으로 진행되는 단계를 구분하여 설명합니다.

### 1. 원하는 것 설명하기

AI가 묻습니다: **"무엇을 만들고 싶으신가요?"**

자연어로 설명하세요. 형식적일 필요는 없습니다 — 문제와 원하는 것을 그냥 설명하면 됩니다. 처음부터 많은 맥락을 제공할수록 추가 질문이 줄어듭니다.

### 2. 요구사항 명확화

AI가 Intent에 대해 **2~4개의 핵심 질문**을 합니다. 일반적인 체크리스트가 아니라 여러분이 설명한 내용에 특화된 질문입니다. 다음과 같은 내용을 물어볼 수 있습니다:

- 구체적인 문제와 영향을 받는 대상
- 관련된 시스템, API, 또는 데이터 소스
- 주요 제약 조건 (성능, 보안, 컴플라이언스)
- 여러분이 생각하는 성공의 모습

### 3. 도메인 탐색 (자동)

AI가 코드베이스와 외부 시스템을 자율적으로 탐색합니다. 이 과정은 백그라운드에서 진행되므로 별도로 할 일이 없습니다. 탐색 대상은 다음과 같습니다:

- **기존 코드** — 아키텍처, 패턴, 컨벤션, 관련 구현체
- **API 및 데이터 소스** — 스키마 인트로스펙션, 샘플 데이터, 사용 가능한 필드
- **외부 문서** — 라이브러리 문서, API 레퍼런스, 모범 사례
- **배포 및 모니터링** — 기존 인프라, 관찰 가능성 패턴, 운영 절차
- **품질 도구** — 품질 게이트로 활용될 테스트 러너, 린터, 타입 체커

기존 프로젝트의 경우, 탐색 단계에서 **지식 레이어**도 부트스트랩됩니다 — 프로젝트의 디자인 언어, 아키텍처 패턴, 도메인 모델을 담은 구조화된 아티팩트입니다.

탐색이 완료되면 AI가 발견한 주요 엔티티, 관계, 데이터 소스를 보여주는 **도메인 모델**을 제시합니다. 정확한지 확인하거나 누락된 부분을 알려주세요.

모니터링 패턴이 발견되고 Intent에 배포 대상이 있는 경우, AI가 이 시점에 모니터링 접근 방식을 함께 확인합니다.

### 4. 디자인 방향 설정 (신규 프로젝트 전용)

그린필드 또는 초기 단계 프로젝트의 경우, AI가 **디자인 방향 선택기**를 제시합니다. 여기서 시각적 아키타입을 선택하고 밀도, 색상 온도, 타이포그래피 대비 등의 파라미터를 조정할 수 있습니다. 이를 통해 일관된 시각적 결과물을 위한 프로젝트의 디자인 지식이 초기화됩니다. 기존 프로젝트는 이 단계를 건너뜁니다.

### 5. 워크플로우 선택

AI가 Intent에 맞는 워크플로우를 추천하고 사용 가능한 모든 옵션을 보여줍니다:

| 워크플로우 | Hat 순서 | 적합한 경우 |
|----------|-------------|----------|
| Default | Planner → Builder → Reviewer | 대부분의 구현 작업 |
| Design | Planner → Designer → Reviewer | UI/UX 디자인 작업 |
| TDD | Test Writer → Implementer → Refactorer → Reviewer | 높은 정확성이 요구되는 코드 |
| Adversarial | Planner → Builder → Red Team → Blue Team → Reviewer | 보안에 민감한 작업 |

하나를 선택하세요. 필요한 경우 개별 Unit에서 Intent 수준의 워크플로우를 재정의할 수 있습니다.

### 6. 성공 기준

AI가 도메인 모델과 요구사항을 바탕으로 **3~7개의 검증 가능한 성공 기준**을 제안합니다. 검토 후 조정하세요. 각 기준은 다음을 충족해야 합니다:

- **구체적** — 모호하지 않을 것
- **측정 가능** — 프로그래밍 방식으로 검증 가능할 것
- **테스트 가능** — 테스트를 작성할 수 있을 것

AI는 비기능적 요구사항(성능 목표, 보안 요구사항, 접근성 수준)도 확인하여 기준에 추가합니다.

### 7. Unit 분해

복잡한 Intent의 경우, AI가 작업을 명확한 경계를 가진 독립적인 조각인 **Unit**으로 분해합니다. 각 Unit에는 다음이 포함됩니다:

- 도메인 모델과 연결된 설명
- 자체 성공 기준
- 의존성 엣지 (먼저 구현되어야 하는 것)
- 분야 (프론트엔드, 백엔드, 디자인 등)

각 Unit을 개별적으로 검토하고 승인, 변경 요청, 또는 재검토를 요청할 수 있습니다.

단순한 Intent(단일 관심사, 단일 코드 영역)는 단일 Unit으로 처리되며 분해가 필요하지 않습니다.

### 8. Git 전략

작업 전달 방식에 대한 두 가지 질문입니다:

1. **전달 전략** — 전체 Intent에 대한 PR 하나, Unit별 개별 PR, 또는 main에 직접 병합
2. **소스 브랜치** — 기본 브랜치 또는 현재 브랜치에서 빌드

이는 Intent별 결정 사항입니다. 프로젝트 수준의 기본값은 `/ai-dlc:setup`에서 설정하세요.

### 9. 품질 게이트

AI가 프로젝트 도구(테스트 러너, 린터, 타입 체커)에서 감지한 품질 게이트를 보여줍니다. 실행 중 적용할 항목을 확인하세요. 게이트는 *강제적*입니다 — 모든 게이트를 통과하기 전까지 AI는 빌드를 중단할 수 없습니다.

### 10. 스펙 검토 (자동)

두 가지 자동화된 검토가 별도 입력 없이 실행됩니다:

1. **스펙 검토** — 완전성, 일관성, YAGNI 위반 여부 확인
2. **적대적 검토** — 누락된 오류 경로, 순환 의존성, 스펙 공백 탐색

신뢰도가 높은 수정 사항은 자동으로 적용됩니다. 나머지 발견 사항은 여러분의 결정을 위해 제시됩니다.

### 11. 인계

구체화가 완료됩니다. 다음 중 무엇을 할지 선택하세요:

- **실행** — 즉시 자율 빌드 루프 시작
- **PR 열기** — 빌드 전에 팀을 위한 스펙 검토 PR 생성

## 구체화 커스터마이징

### 프로젝트 수준 커스터마이징

프로젝트에 `.ai-dlc/ELABORATION.md`를 생성하여 모든 구체화 세션에 적용될 상시 맥락을 제공하세요 — 도메인 지식, 필수 탐색 영역, 컴플라이언스 요구사항, 팀 컨벤션 등을 포함할 수 있습니다.

### 설정 (`/ai-dlc:setup`)

다음 프로젝트 수준 설정이 구체화 동작에 영향을 줍니다:

| 설정 | 효과 |
|---------|--------|
| `default_announcements` | 완료 시 생성할 형식 (변경 로그, 릴리스 노트 등) |
| `default_passes` | 교차 기능 반복 Pass (디자인 → 프로덕트 → 개발) |
| `visual_review` | 구체화 게이트에서 브라우저 기반 검토 UI 사용 |
| `granularity` | Unit 분해 세분화 수준 (coarse / standard / fine) |
| Providers | 티켓팅, 스펙, 디자인, 커뮤니케이션 통합 |

### 자율 모드

`/ai-dlc:autopilot`으로 실행하면 구체화가 최소한의 상호작용으로 진행됩니다 — 질문 대신 합리적인 기본값을 선택합니다. 진정한 모호성, 스펙 모순, 또는 수정 불가능한 검토 결과가 있을 때만 일시 중지합니다.

## 팁

- **처음부터 구체적으로 설명하세요.** 1단계에서 더 많은 세부 정보를 제공할수록 AI의 추가 질문이 줄어듭니다.
- **기준에 이의를 제기하세요.** 제안된 기준이 모호하거나("코드가 깔끔하다") 범위를 벗어난 경우 말씀해 주세요. 기준은 이후 모든 것을 이끌어 갑니다.
- **도메인 모델을 꼼꼼히 검토하세요.** 잘못된 도메인 모델은 잘못된 Unit 스펙으로 이어지고, 결국 잘못된 것을 만들게 됩니다. 이것이 가장 중요한 체크포인트입니다.
- **`/ai-dlc:elaborate {slug}`를 사용하여** 아직 실행이 시작되지 않은 기존 Intent를 수정하세요.
- **`/ai-dlc:followup`을 사용하여** 완료된 Intent를 기반으로 하는 반복 Intent를 생성하세요.

## 구체화 이후의 흐름

구체화 이후의 일반적인 흐름은 다음과 같습니다:

1. **실행** (`/ai-dlc:execute`) — 자율 빌드 루프: Unit별 Planner → Builder → Reviewer
2. **통합** — 모든 Unit 완료 후 교차 Unit 검증
3. **전달 전 검토** — PR 생성 전 전체 diff에 대한 멀티 에이전트 코드 리뷰
4. **PR 생성** — 푸시 및 풀 리퀘스트 열기

**전달 전 검토**(`/ai-dlc:review`)는 특별히 언급할 가치가 있습니다. 전체 diff를 대상으로 새로운 컨텍스트에서 전문화된 검토 에이전트를 실행합니다 — Unit별 검토자가 한 번에 하나의 Unit만 보기 때문에 놓칠 수 있는 문제를 잡아냅니다. 프로젝트별 검토 규칙을 위해 프로젝트의 `REVIEW.md`와 `CLAUDE.md`를 읽고, PR 생성 전에 루프를 돌며 문제를 자동으로 수정합니다.

`/ai-dlc:review`는 독립 실행도 가능합니다 — `/ai-dlc:quick` 이후, 또는 푸시 전 임의의 브랜치에서 실행하여 외부 CI나 검토 봇에 도달하기 전에 문제를 잡을 수 있습니다.
