AI-DLC 도입은 목적지가 아닌 여정입니다. 이 로드맵은 개인적인 실험에서 조직 전체의 실천으로 확장되는 단계적 접근 방식을 제공합니다.

## 1단계: 개인 개발자

한 명의 개발자가 하나의 프로젝트에서 시작하세요. 확장하기 전에 기본기를 완전히 익히는 것이 중요합니다.

### 사전 조건

1단계를 시작하기 전에 다음 사항을 확인하세요:

- **Claude Code 설치** - 개발 환경에서 정상적으로 동작하는지 확인
- **실제 프로젝트** - 연습용 토이 프로젝트가 아닌, 현재 실제로 작업 중인 프로젝트
- **전용 시간 확보** - 초반 몇 세션에서 학습 곡선이 있음을 감안하여 계획
- **열린 마음** - AI-DLC는 처음에 느리게 느껴질 수 있습니다. 과정을 신뢰하세요

### 목표

- [ ] 기본 워크플로우를 사용하여 3~5개의 Unit 완료
- [ ] 네 가지 hats(연구자, 계획자, 빌더, 검토자) 모두 경험
- [ ] hat 전환에 대한 근육 기억 형성
- [ ] 좋은 완료 기준 작성에 대한 직관 개발

### 활동

**첫 번째 세션:**
1. AI-DLC 플러그인 설치
2. 2~3개의 Unit으로 구성된 첫 번째 Intent 생성
3. `/ai-dlc:elaborate`와 `/ai-dlc:execute`를 사용하여 첫 번째 Unit 진행
4. 전체 hat 사이클 완료

**이후 세션:**
- 다양한 워크플로우 유형(TDD, 가설 검증) 실험
- 점점 더 구체적인 완료 기준 작성 연습
- `/clear` 후 재시작할 시점과 계속 진행할 시점 파악

### 성공 지표

| 지표 | 목표 | 측정 방법 |
|--------|--------|----------------|
| 완료된 Unit 수 | 3~5개 | 완료 표시된 `.ai-dlc/unit-*.md` 파일 수 확인 |
| hat 활용도 | 4가지 모두 사용 | 자기 관찰 |
| 기준 구체성 | 지속적 향상 | Unit당 모호한 기준 수 감소 |
| 달성된 자율성 | 일부 AHOTL | 빌더 단계가 개입 없이 실행된 경우 최소 1회 |

### 흔한 함정

| 함정 | 증상 | 해결책 |
|---------|---------|----------|
| 리서치 건너뛰기 | 바로 빌딩으로 넘어가는 경우 | 연구자 hat을 5분 이상 착용하도록 강제 |
| 모호한 기준 | "작동하게 만들기" 식의 기준 | "이것을 프로그래밍적으로 어떻게 검증할까?"라고 자문 |
| 조기 최적화 | 고급 워크플로우를 먼저 시도 | 자연스럽게 느껴질 때까지 기본 워크플로우 유지 |
| 조기 포기 | Unit 중간에 포기 | 평가하기 전에 최소 3개의 Unit 완료 |

### 1단계 체크리스트

- [ ] 플러그인 설치 및 정상 동작 확인
- [ ] 첫 번째 Intent 생성
- [ ] 첫 번째 Unit 완료
- [ ] 네 가지 hats 모두 경험
- [ ] 총 3개의 Unit 완료
- [ ] 개인 워크플로우 선호도 파악
- [ ] 다른 사람들과 경험 공유 준비 완료

## 2단계: 팀 도입

한 명의 개발자가 방법론을 검증한 후, 팀 전체로 확장합니다.

### 사전 조건

2단계를 시작하기 전에 다음 사항을 확인하세요:

- **1단계 챔피언 확보** - 질문에 답하고 좋은 실천 사례를 보여줄 수 있는 사람
- **팀의 동의** - 최소한 관심, 가능하면 열정적인 참여
- **위험 부담이 낮은 프로젝트** - 중요한 릴리스에서 시작하지 말 것
- **문서 준비** - 팀과 이 문서를 공유

### 목표

- [ ] 모든 팀원이 독립적으로 최소 하나의 Unit 완료
- [ ] Intent/Unit 구성에 대한 팀 컨벤션 수립
- [ ] AI-DLC를 기존 워크플로우(PR 리뷰, 스탠드업)에 통합
- [ ] 어떤 상황에서 어떤 워크플로우를 사용할지에 대한 공통 이해 형성

### 도입 방법

**챔피언 모델 (권장)**

1. 챔피언이 팀 미팅에서 실제 작업에 AI-DLC를 시연
2. 팀원들이 챔피언과 페어링하여 첫 번째 Unit 진행
3. 팀원들이 챔피언의 지원을 받으며 독립적으로 작업
4. 팀이 함께 독립적으로 완료된 첫 번째 Unit 검토

**페어 프로그래밍 모델 (대안)**

1. 두 명의 개발자가 함께 Unit 진행
2. 한 명이 주도하고, 다른 한 명이 관찰하며 학습
3. 다음 Unit에서 역할 교체
4. 두 명 모두 나머지 팀원들을 위한 챔피언이 됨

### 컨벤션 수립

팀은 다음 사항에 합의해야 합니다:

| 컨벤션 | 옵션 | 권장 사항 |
|------------|---------|----------------|
| Intent 파일 위치 | 루트, `.ai-dlc/`, 피처 브랜치 | `.ai-dlc/` 디렉토리 |
| Unit 명명 규칙 | 순차적, 설명적, 혼합 | `unit-01-description.md` |
| 커밋 전략 | Unit별, hat별, 피처별 | Unit별 (완료된 Unit당 하나의 커밋) |
| PR 통합 | Intent별, Unit별 | Intent별 (모든 Unit을 하나의 PR에) |

### 통합 포인트

**데일리 스탠드업:**
- "인증 Intent의 3번째 Unit을 작업 중입니다"
- "2번째 Unit에서 블로킹됨 - API 스펙 명확화 필요"

**풀 리퀘스트:**
- PR 설명에 Intent 파일 링크 포함
- 리뷰어가 완료 기준 충족 여부 확인 가능
- Unit 파일이 변경 사항에 대한 컨텍스트 제공

**스프린트 계획:**
- 시간이 아닌 Unit 수로 추정
- 계획 단계에서 피처를 Intent로 분해
- Unit DAG에서 의존성 가시화

### 성공 지표

| 지표 | 목표 | 측정 방법 |
|--------|--------|----------------|
| 팀 도입률 | 100% | 모든 팀원이 최소 하나의 Unit 완료 |
| 일관성 | 높음 | 팀이 프로젝트 전반에 동일한 컨벤션 사용 |
| 품질 | 향상 | 버그 감소, 깔끔한 PR, 더 나은 테스트 커버리지 |
| 속도 | 유지 또는 향상 | 스프린트 완료율 |

### 흔한 함정

| 함정 | 증상 | 해결책 |
|---------|---------|----------|
| 불일치한 도입 | 챔피언만 AI-DLC 사용 | 특정 작업 유형에 필수로 지정 |
| 컨벤션 이탈 | 모두가 다르게 사용 | 컨벤션 문서화 및 준수 강제 |
| 오버헤드 불만 | "이게 더 느려요" | 품질 향상에 집중하고 인내심 갖기 |
| 도구 탓하기 | "AI가 실수했어요" | 기준 및 리뷰 프로세스 개선 |

### 2단계 체크리스트

- [ ] 챔피언 선정 및 준비 완료
- [ ] 팀 소개 완료
- [ ] 모든 팀원이 첫 번째 Unit 완료
- [ ] 컨벤션 문서화
- [ ] 통합 포인트 수립
- [ ] 피드백 수집 및 반영
- [ ] 더 넓은 도입을 위한 준비 완료

## 3단계: 조직 전체

적절한 지원과 거버넌스를 갖추어 AI-DLC를 조직 전체로 확장합니다.

### 사전 조건

3단계를 시작하기 전에 다음 사항을 확인하세요:

- **여러 팀의 성공적인 도입** - 최소 2~3개 팀이 AI-DLC를 효과적으로 사용 중
- **경영진 후원** - 리더십이 방법론을 이해하고 지지
- **교육 리소스** - 문서, 예시, 챔피언 확보
- **지표 프레임워크** - 도입 현황을 측정하고 보고할 수 있는 체계

### 목표

- [ ] AI-DLC가 적합한 작업 유형에 대한 기본 방법론으로 정착
- [ ] 신규 입사자 및 기존 직원을 위한 교육 프로그램 수립
- [ ] 툴링 및 자동화가 AI-DLC 워크플로우 지원
- [ ] 지속적 개선 프로세스 운영

### 제도화

**교육 프로그램:**
- 온보딩에 AI-DLC 소개 포함
- 워크플로우 선택 및 커스텀 워크플로우를 위한 고급 워크숍
- 챔피언 인증 프로그램
- 숙련된 실무자와의 정기 오피스 아워

**툴링 지원:**
- 프로젝트 템플릿에 `.ai-dlc/` 구조 포함
- 완료 기준을 인식하는 CI/CD
- 도입 지표를 추적하는 대시보드
- 미완료 Unit에 대한 자동 알림

**거버넌스:**
- AI-DLC가 필수인 경우와 선택적인 경우에 대한 가이드라인
- Intent 및 Unit에 대한 품질 기준
- 커스텀 워크플로우 검토 프로세스
- 방법론 개선을 위한 피드백 채널

### 팀 간 조율

여러 팀에 걸친 대규모 피처의 경우:

```
feature-xyz/
  intent.md              # High-level feature intent
  team-backend/
    intent.md            # Backend team's intent
    unit-01-api.md
    unit-02-database.md
  team-frontend/
    intent.md            # Frontend team's intent
    unit-01-components.md
    unit-02-integration.md
  team-mobile/
    intent.md            # Mobile team's intent
    unit-01-screens.md
```

각 팀은 자신의 Intent와 Unit을 소유하며, 팀 경계를 넘는 의존성은 명시적으로 선언됩니다.

### 성공 지표

| 지표 | 목표 | 측정 방법 |
|--------|--------|----------------|
| 도입률 | 적합한 프로젝트의 80% 이상 | `.ai-dlc/` 자동 스캔 |
| 교육 완료율 | 개발자 100% | LMS 추적 |
| 품질 향상 | 측정 가능한 수준 | 버그 발생률, PR 수정 횟수, 테스트 커버리지 |
| 개발자 만족도 | 높음 | 설문조사, 이직률 |

### 지속적 개선

1. **분기별 검토** - 방법론 효과성 평가
2. **회고** - 피드백 수집 및 반영
3. **실험** - 새로운 워크플로우, 도구, 실천 방법 시도
4. **공유** - 성공적인 패턴 문서화 및 전파

### 3단계 체크리스트

- [ ] 경영진 후원 확보
- [ ] 교육 프로그램 시작
- [ ] 툴링 지원 구현
- [ ] 거버넌스 프레임워크 수립
- [ ] 팀 간 조율 체계 운영
- [ ] 지표 대시보드 운영
- [ ] 지속적 개선 프로세스 활성화

## 타임라인 가이드

도입 타임라인은 조직 규모와 문화에 따라 다릅니다. 다음은 일반적인 프레임워크입니다:

| 단계 | 소규모 팀 (5~10명) | 중간 규모 조직 (50~200명) | 대규모 조직 (500명 이상) |
|-------|-------------------|---------------------|------------------|
| 1단계 | 1~2 스프린트 | 1~2 스프린트 | 2~4 스프린트 |
| 2단계 | 2~3 스프린트 | 3~6 스프린트 | 6~12 스프린트 |
| 3단계 | 해당 없음 | 6~12 스프린트 | 12~24 스프린트 |

**핵심 원칙:** 서두르지 마세요. 지속 가능한 도입에는 시간이 필요합니다. 다섯 팀이 AI-DLC를 형편없이 사용하는 것보다 한 팀이 탁월하게 사용하는 것이 훨씬 낫습니다.
