AI-DLC는 관심사를 분리하기 위해 "hat" 메타포를 사용합니다. 각 hat은 고유한 사고방식, 책임 범위, 그리고 커뮤니케이션 스타일을 나타냅니다. Hats는 **워크플로우** 단위로 구성되며, 수행하는 작업의 유형에 따라 서로 다른 hat 조합을 사용합니다.

## 왜 Hats인가?

hat 시스템은 다음과 같은 문제를 방지합니다:

- **컨텍스트 이탈**: 계획과 구현 사이를 무의식적으로 오가는 현상
- **범위 확장**: 계획되지 않은 기능을 구현하는 현상
- **품질 타협**: "일단 배포하자"는 이유로 검토를 건너뛰는 현상
- **역할 혼란**: 코드를 공격하는 동시에 방어하려는 현상

hat을 명시적으로 전환함으로써 집중력을 유지하고 각 단계가 충분한 주의를 받도록 보장합니다. 도메인 리서치는 실행이 시작되기 전, Mob Elaboration(`/ai-dlc:elaborate`) 단계에서 이루어집니다.

## 핵심 Hats

이 hats는 기본 실행 워크플로우의 근간을 이룹니다: **Planner -> Builder -> Reviewer**. 또한 다른 워크플로우에서도 재사용됩니다.

### Planner

Unit 요구사항을 기반으로 다음 Bolt에 대한 전술적 실행 계획을 수립합니다.

- 현재 Unit을 검토하고 남은 완료 기준을 파악합니다
- 다음 Bolt에 대한 구체적이고 실행 가능한 계획을 수립합니다
- 영향도가 높은 기준을 우선순위화하고 작업을 검증 가능한 단계로 분해합니다
- 잠재적 장애 요소를 표시하고 대안적 접근 방식을 제안합니다
- Builder가 모호함 없이 따를 수 있도록 계획을 저장합니다

### Builder

백프레셔를 피드백으로 활용하여 완료 기준을 충족하는 코드를 구현합니다.

- Planner의 계획을 따르며 작고 검증 가능한 단위로 작업합니다
- 각 변경 후 백프레셔 검사(테스트, 린트, 타입)를 실행합니다
- 테스트 실패와 린트 오류를 구현 지침으로 활용합니다
- 스크래치패드에 진행 상황과 장애 요소를 기록합니다
- 작동하는 단위를 커밋하고 완료를 알리거나 반복 작업을 수행합니다

### Reviewer

코드 리뷰와 테스트 검증을 통해 구현이 완료 기준을 충족하는지 확인합니다.

- 프로그래밍 방식의 검증으로 각 완료 기준을 개별적으로 확인합니다
- 전체 테스트 스위트를 실행하고 모든 새 코드에 대응하는 테스트가 있는지 확인합니다
- 코드 품질, 보안 고려사항, 엣지 케이스 처리를 검토합니다
- 심각도에 따라 우선순위가 정해진 구체적이고 실행 가능한 피드백을 제공합니다
- 근거와 함께 명확한 APPROVE 또는 REQUEST CHANGES 결정을 내립니다

## 가설 Hats

버그의 체계적인 조사를 위한 가설 워크플로우에서 사용됩니다: **Observer -> Hypothesizer -> Experimenter -> Analyst**. 이 워크플로우는 디버깅에 과학적 방법을 적용합니다.

### Observer

결론으로 성급하게 도약하지 않고 체계적인 관찰을 통해 버그에 대한 데이터를 수집합니다.

- 버그 재현을 시도하고 정확한 재현 단계를 문서화합니다
- 오류 메시지, 스택 트레이스, 오류 코드를 수집합니다
- 버그가 처음 나타난 시점의 타임라인을 수립합니다
- 연관된 오류를 찾기 위해 애플리케이션 및 시스템 로그를 검토합니다
- 결론 없이 관찰 내용만 정리합니다 -- 데이터만 기록합니다

### Hypothesizer

관찰 결과를 바탕으로 버그 원인에 대한 검증 가능한 이론을 수립합니다.

- 모든 Observer 데이터를 검토하고 주요 증상과 패턴을 파악합니다
- 명백한 원인과 비명백한 원인을 모두 포괄하는 최소 세 가지 가설을 생성합니다
- 각 가설에 대한 확인 및 반증 기준을 정의합니다
- 가능성과 테스트 용이성의 곱으로 가설의 우선순위를 정합니다
- Experimenter를 위한 명확한 테스트 계획을 문서화합니다

### Experimenter

통제된 실험을 통해 가설을 체계적으로 테스트하여 근본 원인을 파악합니다.

- 단일 변수를 격리하는 최소한의 실험을 설계합니다
- 설계에 따라 정확하게 실험을 수행하고 모든 관찰 결과를 기록합니다
- 결과를 확인/반증 기준과 비교합니다
- 근본 원인이 발견될 때까지 우선순위 순서대로 가설을 검토합니다
- 모든 가설이 반증된 경우 새로운 데이터와 함께 Hypothesizer로 돌아갑니다

### Analyst

실험 결과를 평가하고 확인된 근본 원인을 바탕으로 수정 사항을 구현합니다.

- 실험적 증거를 검토하고 근본 원인이 모든 증상을 설명하는지 확인합니다
- 증상만이 아닌 근본 원인을 해결하는 수정 방안을 설계합니다
- 최소한의 집중된 변경으로 수정 사항을 구현합니다
- 수정 전에 실패하고 수정 후에 통과하는 회귀 테스트를 추가합니다
- 원래 버그가 해결되었고 회귀가 발생하지 않았는지 확인합니다

## TDD Hats

클래식한 Red-Green-Refactor 사이클을 따르는 TDD 워크플로우에서 사용됩니다: **Test Writer -> Implementer -> Refactorer**.

### Test Writer

구현 전에 예상 동작을 정의하는 실패하는 테스트를 작성합니다 (RED 단계).

- 작고 테스트 가능한 동작 하나를 선택하고 구현 전에 테스트를 작성합니다
- 명세처럼 읽히는 설명적인 테스트 이름을 사용합니다
- 테스트가 올바른 이유(구문 오류가 아닌 구현 누락)로 실패하는지 확인합니다
- 테스트를 단일 동작에 집중시킵니다
- 다른 개발자가 Intent를 이해할 수 있도록 비명백한 테스트 로직을 문서화합니다

### Implementer

실패하는 테스트를 통과시키기 위한 최소한의 코드를 작성합니다 (GREEN 단계).

- 실패하는 테스트가 기대하는 것을 정확히 읽고 이해합니다
- 테스트를 통과시키기에 충분한 코드만 작성합니다 -- 그 이상은 작성하지 않습니다
- 조기 최적화, 일반화, 추상화를 자제합니다
- 전체 테스트 스위트를 실행하여 회귀가 없는지 확인합니다
- 정리는 Refactorer에게 맡깁니다 -- 지저분하더라도 동작하는 것이 목표입니다

### Refactorer

테스트를 통과시킨 상태를 유지하면서 코드 품질을 개선합니다 (REFACTOR 단계).

- 중복, 불명확한 네이밍, 단순화 기회를 파악합니다
- 한 번에 하나씩 작은 변경을 가하고 각 변경 후 테스트를 실행합니다
- Intent를 드러내도록 변수와 함수의 이름을 변경합니다
- 적절한 추상화를 사용하여 반복되는 코드를 함수로 추출합니다
- 언제 멈출지 압니다 -- 완벽함은 진보의 적입니다

## 적대적 Hats

보안 중심 개발을 위한 적대적 워크플로우에서 사용됩니다: **Planner -> Builder -> Red Team -> Blue Team -> Reviewer**. Planner, Builder, Reviewer hats는 핵심 워크플로우와 동일하게 작동하며, 적대적 hats는 최종 검토 전에 공격-방어 사이클을 추가합니다.

### Red Team

보안 테스트와 취약점 발견을 통해 구현을 공격하려 시도합니다.

- 공격 표면을 열거합니다: 입력값, API 파라미터, 헤더, 인증 경계
- 인젝션 취약점을 테스트합니다 (SQL 인젝션, XSS, 커맨드 인젝션, 경로 탐색)
- 인증 우회 및 권한 상승을 시도합니다 (수평적 및 수직적)
- 오류, 로그, URL 파라미터에서 정보 노출을 확인합니다
- 심각도 등급과 재현 단계를 포함하여 모든 발견 사항을 문서화합니다 -- 수정은 하지 않습니다

### Blue Team

적절한 보안 제어와 테스트로 Red Team이 발견한 취약점을 수정합니다.

- 심각도에 따라 발견 사항의 우선순위를 정하고 Critical 및 High 문제를 먼저 처리합니다
- 증상만이 아닌 보안 코딩 패턴을 사용하여 근본 원인을 수정합니다
- 각 취약점을 재현하는 보안 테스트를 추가합니다 (수정 전 실패, 수정 후 통과)
- 다중 보호 레이어로 심층 방어를 구현합니다
- Red Team 공격을 재실행하여 이전의 모든 공격이 이제 실패하는지 확인합니다

## Design Hat

디자인 워크플로우에서 사용됩니다: **Planner -> Designer -> Reviewer**. Planner와 Reviewer hats는 핵심 워크플로우와 동일하게 작동합니다.

### Designer

시각적 디자인, UI 목업, 사용자 경험 흐름을 만듭니다.

- 디자인 문제를 명확히 하고 사용자 목표와 불편 사항을 파악합니다
- 여러 디자인 대안을 생성하고 트레이드오프를 제시합니다
- 사용자 피드백을 반영하고 디자인 결정 사항을 문서화합니다
- 반응형 동작, 인터랙션 상태, 접근성 요구사항을 명세합니다
- 프로젝트 디자인 시스템의 명명된 토큰을 참조하는 디자인 명세를 작성합니다

## Integration Hat

Intent의 모든 Unit이 완료된 후 크로스 워크플로우, Intent 수준의 검증에 사용됩니다.

### Integrator

병합된 Intent 브랜치에서 모든 Unit이 함께 작동하는지 검증하는 최종 Intent 수준의 검증을 수행합니다.

- 모든 Unit 브랜치가 병합된 Intent 브랜치가 깨끗한지 확인합니다
- 결합된 코드베이스에서 전체 백프레셔 스위트(테스트, 린트, 타입)를 실행합니다
- 여러 Unit에 걸친 Intent 수준의 성공 기준을 검증합니다
- 통합 격차를 찾기 위해 크로스 Unit 경계, 공유 상태, API, 데이터 흐름을 확인합니다
- 명확한 ACCEPT 또는 REJECT 결정을 내리고 필요한 경우 재작업이 필요한 특정 Unit을 명시합니다

## Hat 전환

Hat 전환은 사용 중인 워크플로우에 따라 다릅니다. 각 워크플로우는 자체 순서를 정의합니다:

- **Core**: Planner -> Builder -> Reviewer
- **Hypothesis**: Observer -> Hypothesizer -> Experimenter -> Analyst
- **TDD**: Test Writer -> Implementer -> Refactorer (동작별 반복)
- **Adversarial**: Planner -> Builder -> Red Team -> Blue Team -> Reviewer
- **Design**: Planner -> Designer -> Reviewer

모든 워크플로우 내에서 필요한 경우 이전 단계로 전환할 수 있습니다:

- **Builder -> Planner**: 새로운 발견을 바탕으로 계획 수정이 필요한 경우
- **Reviewer -> Builder**: 검토에서 수정해야 할 문제가 발견된 경우
- **Experimenter -> Hypothesizer**: 모든 가설이 반증되어 새로운 이론이 필요한 경우
- **Analyst -> Observer**: 수정이 실패하여 추가 데이터 수집이 필요한 경우

핵심은 전환을 *의도적으로* 만드는 것입니다. 표류하지 말고 -- 명시적으로 전환하세요. 각 워크플로우의 전체 생명주기에 대한 자세한 내용은 [워크플로우](/docs/workflows) 문서를 참조하세요.

## 효과적인 Hat 사용을 위한 팁

1. **Hat을 선언하세요**: 각 단계를 시작할 때 어떤 hat을 쓰고 있는지 명시적으로 밝히세요
2. **역할에 충실하세요**: 계획 중에 구현으로 앞서 나가려는 충동을 억제하세요
3. **프로세스를 신뢰하세요**: 답을 "알고 있다"고 생각할 때도 이전 단계에서 종종 예상치 못한 것이 드러납니다
4. **경계를 존중하세요**: Red Team은 취약점을 문서화하지만 수정하지 않습니다; Blue Team은 수정하지만 새로운 것을 발견하지 않습니다
5. **백프레셔가 이끌도록 하세요**: 테스트, 린트, 타입은 장애물이 아닌 피드백 메커니즘입니다
