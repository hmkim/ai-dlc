Anthropic 엔지니어링 팀은 최근 [Harness Design for Long-Running Application Development](https://www.anthropic.com/engineering/harness-design-long-running-apps)를 발표했다. 복잡하고 지속적인 AI 작업을 위한 멀티 에이전트 오케스트레이션 시스템 구축에 관한 상세한 내용을 담은 글이다. 이 글은 **하네스(harness)**라는 용어를 소개하며, 이를 AI 에이전트를 구조화된 단계에 따라 조율하고, 장기 실행 작업 전반에 걸쳐 컨텍스트를 관리하며, 모델이 단독으로 수행할 수 없는 작업에 대한 가정을 인코딩하는 스캐폴딩으로 정의한다.

이 글을 읽으면서, 우리가 이미 만들어 놓은 것에 비로소 이름이 생긴 것 같은 느낌이 들었다.

AI-DLC는 하네스다. 이를 하네스로 이해하면 AI-DLC가 무엇을 하는지, 왜 작동하는지, 그리고 어디로 향하는지가 명확해진다.

## 하네스란 무엇인가?

Anthropic의 글은 하네스를 복잡한 작업을 전문화된 역할들이 협력하여 처리하도록 분해하는 멀티 에이전트 오케스트레이션 시스템으로 설명한다. 단일 모델에 모든 것을 처음부터 끝까지 맡기는 대신, 하네스는 별도의 에이전트에 각기 다른 책임을 부여한다. 간략한 프롬프트를 포괄적인 명세로 변환하는 플래너, 실제 작업을 수행하는 제너레이터, 구체적인 기준과 외부 도구를 활용해 품질을 평가하는 이밸류에이터가 그 예다.

그들의 경험에서 몇 가지 설계 원칙이 도출된다:

**에이전트 간 핸드오프를 위한 파일 기반 통신.** 에이전트들은 직접 대화가 아닌 구조화된 파일을 통해 비동기적으로 소통한다. 한 에이전트가 파일을 작성하면, 다음 에이전트가 이를 읽고 응답한다. 이를 통해 동기식 조율의 오버헤드를 없애고, 어떤 에이전트든 참조할 수 있는 영속적인 아티팩트를 생성한다.

**제너레이터-이밸류에이터 피드백 루프.** 이 글의 핵심 통찰은 다음과 같다: "작업을 수행하는 에이전트와 그것을 평가하는 에이전트를 분리하는 것이 강력한 레버임이 입증되었다." 모델은 자신의 출력을 칭찬하는 경향이 있기 때문에 자기 평가는 실패한다. 회의적인 시각을 갖도록 조정된 별도의 이밸류에이터가 구체적인 피드백을 제공하여 여러 사이클에 걸친 반복적 개선을 이끌어낸다.

**구조화된 핸드오프를 통한 컨텍스트 리셋.** 이전 내용을 요약하여 컨텍스트를 압축하는 대신, 하네스는 컨텍스트 윈도우를 완전히 비우고 새로 시작한다. 이는 두 가지 문제를 해결한다: 모델이 긴 작업에서 일관성을 잃는 문제와, 저자들이 "컨텍스트 불안"이라고 부르는 현상, 즉 모델이 컨텍스트 한계에 가까워졌다고 인식할 때 작업을 조기에 마무리하려는 경향이다. 리셋은 깨끗한 출발점을 제공하지만, 다음 에이전트가 원활하게 작업을 이어받을 수 있도록 충분한 상태 정보를 담은 핸드오프 아티팩트가 필요하다.

**가정 원칙.** 이 글에서 가장 범용적으로 적용 가능한 통찰이다: "하네스의 모든 구성 요소는 모델이 단독으로 할 수 없는 것에 대한 가정을 인코딩하며, 그 가정들은 스트레스 테스트를 받을 가치가 있다." 오케스트레이션 스캐폴딩의 각 요소는 모델이 그것 없이 실패했기 때문에 존재한다. 그러나 모델의 역량은 변한다. Opus 4.6이 계획 수립, 장문 컨텍스트 처리, 자기 수정 능력의 향상과 함께 등장했을 때, 저자들은 Opus 4.5에서 필수적이었던 구성 요소들을 체계적으로 제거했다. 스프린트 기반 분해도 그 중 하나였는데, 새로운 모델은 더 긴 일관된 시퀀스로 이를 처리할 수 있었다. 이밸류에이터는 스프린트별 검토에서 최종 단계 검증으로 전환되었다. 모델이 더 나아졌기 때문에 하네스는 더 단순해졌다.

그들이 권장하는 방식은 급진적인 재구성이 아닌, 한 번에 하나의 구성 요소를 제거하고 그 영향을 측정하는 것이다.

## 매핑

AI-DLC와 Anthropic의 하네스는 동일한 설계 공간을 점유한다. 개념들은 직접적으로 대응된다:

| 하네스 개념 (Anthropic) | AI-DLC 대응 요소 |
|---|---|
| 전문화된 에이전트 역할 (플래너, 제너레이터, 이밸류에이터) | Hat 기반 워크플로우 (플래너, 빌더, 리뷰어) |
| 파일 기반 에이전트 간 통신 | 파일 아티팩트로서의 Intent 명세, Unit 명세, 운영 계획 |
| 제너레이터-이밸류에이터 피드백 루프 | 실행, 리뷰, 실패/진행 사이클 (Bolt) |
| 품질을 이끄는 외부 평가 | 백프레셔 훅, 완료 기준, Stop 게이트 |
| 구조화된 핸드오프를 통한 컨텍스트 리셋 | 파일 아티팩트로부터 임시 상태를 재구성하는 `/ai-dlc:resume` 스킬 |
| "모든 구성 요소는 가정을 인코딩한다" | 각 hat과 단계는 가드레일을 인코딩한다 |
| 하네스 복잡성은 모델 역량에 따라 감소해야 한다 | 어떤 스캐폴딩이 여전히 필요한지 정기적으로 재평가 |

어휘는 다르다. 아키텍처는 닮아 있다.

AI-DLC의 hats는 Anthropic의 전문화된 에이전트 역할에 해당한다. 두 시스템 모두 단일한 에이전트가 모든 것을 한꺼번에 처리하도록 두는 대신, 계획 수립, 생성, 평가라는 별개의 책임을 분리된 운영 모드에 부여한다. AI-DLC의 파일 아티팩트(Intent 명세, Unit 명세, 스크래치패드, 반복 상태)는 Anthropic의 파일 기반 에이전트 간 통신과 동일한 패턴이다: 컨텍스트 경계를 넘어 유지되며 핸드오프를 가능하게 하는 영속적이고 구조화된 상태다. Bolt 사이클, 즉 실행, 리뷰, 실패 또는 진행은 명시적으로 사람이 볼 수 있는 전환을 갖춘 제너레이터-이밸류에이터 피드백 루프다. 그리고 파일 아티팩트로부터 임시 세션 상태를 완전히 재구성하는 `/ai-dlc:resume`는 구조화된 핸드오프를 갖춘 컨텍스트 리셋이다.

이 일치는 우연이 아니다. 이는 동일한 근본적인 문제에 대한 수렴적 해결책이다: 모델은 외부 구조 없이는 긴 컨텍스트에 걸쳐 복잡한 작업을 지속할 수 없다.

## AI-DLC가 갈라지는 지점

매핑은 유사하지만, 세 가지 차이점이 중요하다.

### 자율적이 아닌, 협력적

Anthropic의 글에서 설명하는 하네스는 자율적인 에이전트 간 루프다. 제너레이터가 출력을 생성한다. 이밸류에이터가 이를 평가한다. 루프가 반복된다. 사람은 시스템을 구성하고 최종 결과를 검토하지만, 그 사이의 실행은 밀봉되어 있다.

AI-DLC는 인간의 판단을 중심에 둔다.

사람은 AI와 함께 hats를 착용하고, 단계 간 전환을 승인하며, 구성 중에 명세를 `/ai-dlc:refine`하거나 리뷰를 `/ai-dlc:fail`하여 작업을 되돌려 보낼 수 있다. HITL(인간이 루프 안에), OHOTL(관찰자, 인간이 루프 위에), AHOTL(자율, 인간이 루프 밖에)의 세 가지 운영 모드를 통해 팀은 Intent별로 자율성 수준을 조절할 수 있다. 하네스는 완전한 자율성을 *지원*하지만, 이를 *가정*하지는 않는다.

이는 의도적인 설계 선택이다. [Dark Factories and the Loop](/blog/dark-factories-and-the-loop)에서 주장했듯이, 다크 팩토리는 구축하는 시스템이 아니라 조절하는 노브다. 어떤 작업은 완전한 자율성이 적합하고, 어떤 작업은 긴밀한 감독이 필요하다. 동일한 하네스가 아키텍처 변경 없이 두 가지 모두를 지원해야 한다. 보안에 민감한 인증 플로우와 일상적인 의존성 업그레이드에 서로 다른 도구가 필요해서는 안 된다. 단지 동일한 도구의 설정만 달라질 뿐이다.

Anthropic의 하네스는 자율 실행에서의 처리량을 최적화한다. AI-DLC는 전체 자율성 스펙트럼에 걸친 적응성을 최적화한다.

### SDLC 네이티브 구조

Anthropic의 글에 나오는 하네스는 작업 범용적이다. 그들은 게임 메이커, DAW, 웹사이트 빌더를 구축했다. 하네스 패턴은 작업을 계획-생성-평가 사이클로 분해할 수 있는 모든 도메인에 적용된다.

AI-DLC는 도메인 특화적이다. 소프트웨어 개발 라이프사이클 개념에 매핑된다: Intent는 에픽, Unit은 티켓, Bolt는 스프린트다. 이 특수성은 제한이 아닌 기능이다. 범용 오케스트레이션이 가질 수 없는 레버리지를 하네스에 부여한다.

품질 평가를 예로 들어보자. Anthropic의 하네스는 출력 품질을 평가하기 위해 LLM 이밸류에이터에 의존하며, 이 글은 이것이 얼마나 많은 작업을 요구하는지 솔직하게 인정한다. 기본 상태에서 이밸류에이터는 관대하고 피상적으로 테스트한다. 엄격한 QA를 달성하려면 모델 판단과 인간 평가 간의 차이를 기반으로 한 반복적인 프롬프트 개선이 필요했다. 그들은 주관적인 기준을 구체적이고 채점 가능한 표준으로 변환했으며, "박물관 수준의 품질"과 같은 구체적인 표현조차 출력 방향에 의미 있는 영향을 미친다는 것을 발견했다.

AI-DLC는 소프트웨어 특화 품질 게이트를 백프레셔로 인코딩함으로써 이 문제의 상당 부분을 우회한다. 테스트는 통과하거나 통과하지 못한다. 타입은 체크되거나 체크되지 않는다. 린터는 깨끗하거나 그렇지 않다. 이것들은 LLM의 판단이 아니라 개발 툴체인 자체에서 나오는 결정론적 신호다. 모델이 자신의 코드에 버그가 있다는 것을 납득할 필요가 없다. 테스트 스위트가 직접 알려주고, 하네스는 게이트가 충족될 때까지 진행을 차단한다.

이것이 LLM 기반 평가의 필요성을 완전히 없애지는 않는다. 완료 기준은 여전히 Intent가 충족되었는지에 대한 판단을 요구한다. 그러나 결정론적 백프레셔 레이어가 기계적인 품질 문제를 처리함으로써, 주관적 평가 레이어는 더 높은 수준의 관심사에 집중할 수 있다: 이 구현이 실제로 문제를 해결하는가? API가 직관적인가? 아키텍처가 합리적인가?

도메인 특수성은 결정론적 품질 게이트를 제공한다. 범용 하네스는 품질 평가를 전적으로 LLM 판단을 통해 해결해야 한다.

### 에이전트 SDK가 아닌 플러그인 인프라

Anthropic의 하네스는 Claude Agent SDK를 사용하여 별도의 에이전트 프로세스를 오케스트레이션한다. 각 에이전트는 자체 컨텍스트 윈도우를 가진 별개의 서브프로세스이며, 하네스가 파일 기반 통신을 통해 이를 조율한다. 하네스는 에이전트를 외부에서 관리하는 별도의 오케스트레이션 레이어다.

AI-DLC는 Claude Code의 플러그인 시스템, 즉 스킬, 훅, CLAUDE.md 규칙을 사용하여 단일 Claude Code 세션 *내에서* 동작을 형성한다. 스킬은 구조화된 명령을 제공한다(`/ai-dlc:elaborate`, `/ai-dlc:resume`, `/ai-dlc:refine`). 훅은 도구 호출 경계에서 백프레셔를 강제한다. CLAUDE.md 규칙은 세션 전반에 걸쳐 유지되는 컨텍스트와 제약을 주입한다. Agent Teams가 활성화되면 플러그인이 독립적인 팀원을 생성하지만, 오케스트레이션은 여전히 별도의 SDK 레이어가 아닌 플러그인 프리미티브를 통해 흐른다.

이는 하네스가 곧 개발 환경임을 의미한다. 별도로 설치, 구성, 유지 관리할 시스템이 없다. 플러그인을 설치하면 Claude Code 세션이 구조화된 워크플로우, 품질 게이트, 컨텍스트 관리 기능을 갖추게 된다. 하네스는 작업이 이루어지는 곳에 존재한다.

트레이드오프는 실재한다. Agent SDK 방식은 에이전트 오케스트레이션에 대한 더 많은 제어권을 제공한다. 에이전트를 병렬로 실행하고, 수명 주기를 명시적으로 관리하며, 커스텀 통신 프로토콜을 구축할 수 있다. 플러그인 방식은 개발자 경험과의 더 긴밀한 통합을 제공한다. 하네스는 호출하기 전까지 보이지 않으며, 일반적인 Claude Code 워크플로우를 대체하는 것이 아니라 향상시킨다.

두 가지 모두 유효한 아키텍처다. 각각 다른 것을 최적화한다.

## 스트레스 테스트 원칙

이 글에서 가장 범용적으로 적용 가능한 통찰은 별도의 섹션을 할애할 가치가 있다: 하네스의 모든 구성 요소는 모델이 단독으로 할 수 없는 것에 대한 가정을 인코딩한다. 그 가정이 더 이상 사실이 아닐 때, 해당 구성 요소는 오버헤드가 된다.

AI-DLC의 구성 요소들도 가정을 인코딩한다:

- **구현으로부터 정교화를 분리**하는 것은 기회가 주어지면 모델이 계획과 구축을 혼동할 것이라고 가정한다. 강제된 분리 없이는 명세 중간에 코드를 작성하기 시작한다.
- **필수 리뷰 단계**는 명시적으로 멈추고 평가하도록 지시받지 않으면 모델이 검증을 건너뛸 것이라고 가정한다. 리뷰어 hat 없이는 조기에 완료를 선언한다.
- **백프레셔 훅**은 자동화된 게이트 없이는 모델이 지름길을 택할 것이라고 가정한다. 테스트 실패와 린트 오류에 대한 Stop 훅 없이는 "나중에 수정"하고 결코 돌아오지 않는다.
- **Hat 전환**은 명시적인 역할 전환 없이는 모델이 집중력을 잃는다고 가정한다. 빌더에서 리뷰어로의 전환 없이는 여전히 빌더 모드에서 자신의 작업을 리뷰하며 아무 문제도 발견하지 못한다.

이러한 가정들은 AI-DLC가 설계될 당시 옳았다. 현재 모델들에서도 여전히 옳다. 그러나 "현재"는 움직이는 목표다.

Anthropic은 이를 구체적으로 입증했다. 스프린트 기반 분해는 Opus 4.5에서 필수적인 스캐폴딩이었다. 그것 없이는 모델이 대규모 작업에 걸쳐 일관된 작업을 유지할 수 없었다. Opus 4.6은 더 긴 시퀀스를 기본적으로 처리했고, 스프린트 분해는 실제로 출력 품질을 저하시키는 불필요한 오버헤드가 되었다. 이를 제거하자 결과가 개선되었다.

AI-DLC의 구성 요소들에도 동일한 일이 일어날 것이다. 미래의 어떤 모델은 명시적인 hat 전환 없이도 일관되게 계획하고 구축할 수 있을지 모른다. 미래의 어떤 모델은 별도의 리뷰 단계 없이도 엄격하게 자기 평가를 할 수 있을지 모른다. 미래의 어떤 모델은 백프레셔 훅 없이도 품질 기준을 유지할 수 있을지 모른다.

그런 일이 발생했을 때, 올바른 대응은 스캐폴딩을 방어하는 것이 아니다. 그것을 제거하고, 영향을 측정하고, 단순화하는 것이다. 하네스는 시간이 지남에 따라 더 가벼워져야 한다. 가벼워지지 않는다면, 모델이 해당 차원에서 개선되지 않았거나, 팀이 자신들의 가정을 스트레스 테스트하지 않고 있는 것이다.

Anthropic의 글은 한 번에 하나의 구성 요소를 제거하고 측정할 것을 권장한다. 우리도 이 접근 방식을 지지한다. AI-DLC의 모듈식 구조, 즉 hats는 독립적인 파일이고, 훅은 개별적으로 구성 가능하며, 워크플로우는 조합 가능한 YAML로 이루어져 있다는 점은 바로 이러한 종류의 점진적 단순화를 염두에 두고 설계되었다.

## 이것이 의미하는 바

AI-DLC를 하네스로 자리매김하는 것은 세 가지 효과를 가져온다.

**사람들에게 즉각적인 멘탈 모델을 제공한다.** Anthropic의 글을 읽었다면, AI-DLC가 어떤 범주에 속하는지 알 수 있다. 장기 실행 AI 에이전트 작업을 위한 오케스트레이션 스캐폴딩이다. 구조화된 단계를 통해 전문화된 역할을 조율하고, 상태 관리를 위해 파일 아티팩트를 사용하며, 품질 기준을 자동화된 게이트로 인코딩한다. 전체 방법론을 이해하지 않아도 그것이 어떤 종류의 것인지 이해할 수 있다.

**스캐폴딩이 의도적이며 진화해야 한다는 것을 명확히 한다.** hats, 단계, 훅, 전환, 이것들은 관료주의가 아니다. 특정하고 식별 가능한 모델의 한계를 보완하는 하중을 지탱하는 구조다. 모든 구성 요소는 그것을 제거했을 때 출력이 나빠졌기 때문에 존재한다. 그리고 모든 구성 요소는 모델이 개선됨에 따라 재평가되어야 한다. AI-DLC를 하네스로 이해하면 단순화가 퇴보가 아니라 시스템이 의도한 대로 작동하는 것임이 명확해진다.

**AI-DLC를 더 넓은 설계 공간과 연결한다.** Anthropic은 하네스 설계 패턴을 발표하고 있다. 다른 팀들도 자체 오케스트레이션 시스템을 구축하고 있다. 복잡하고 장기 실행되는 작업을 통해 AI 에이전트를 조율하는 문제는 특정 도구나 방법론에 국한되지 않는다. AI-DLC를 하네스로 명명함으로써, 우리는 이러한 시스템이 어떤 모습이어야 하는지, 어떻게 진화해야 하는지, 어떤 원칙이 그 설계를 지배하는지에 관한 대화에 참여한다. 이 공간에서 구축하는 모든 사람에게 그 답은 중요하다.

AI-DLC는 Claude Code의 플러그인 프리미티브 위에 구축된 협력적이고 SDLC 특화된 하네스다. 이를 하네스로 이해하는 것이 AI-DLC가 무엇을 하는지, 그리고 언제 그 일부를 단순화해야 하는지를 이해하는 가장 명확한 방법이다.
