AI-DLC에는 그린필드 문제가 있었다. 모든 진입점이 새로운 것을 만든다는 전제 위에 설계되어 있었다.

`/ai-dlc:elaborate`는 빈 Intent에서 시작하여 아직 존재하지 않는 작업에 대한 명세, 분해, 계획 수립 과정을 안내한다. `/ai-dlc:followup`은 이전 Intent를 반복적으로 개선하지만, 오직 AI-DLC를 통해 처음 만들어졌고 아티팩트가 이미 디스크에 존재하는 경우에만 동작한다. 팀이 수년간 전통적인 방식으로 소프트웨어를 출시한 뒤에 AI-DLC를 도입했다면, 그 기존 기능들은 이 방법론에서 보이지 않는 존재였다. Intent 파일도 없고, Unit 명세도 없고, 운영 계획도 없다. `auth-system`이 방법론에 등록된 적이 없으니 `/ai-dlc:operate auth-system`을 실행할 방법도 없었다.

이것이 바로 브라운필드 격차다. 실제 팀 대부분은 제로에서 시작하지 않는다. 인증 시스템, 결제 파이프라인, 알림 서비스 — 실제 사용자와 실제 테스트, 실제 운영 이력을 가진 프로덕션 기능들이 이미 존재한다. 그런 팀에게 "AI-DLC는 훌륭하지만, 다음에 새로 만드는 것에만 적용됩니다"라고 말하는 것은 진지한 답변이 아니다.

`/ai-dlc:adopt`가 이 격차를 해소한다.

## Adopt의 역할

Adopt는 기존 기능을 완전한 AI-DLC 아티팩트 — Intent, Unit, 디스커버리, 운영 계획 — 로 역공학하되, 프로덕션 코드 한 줄도 수정하지 않는다. 기능은 이미 동작하고 있다. 코드는 이미 배포되어 있다. Adopt는 그것을 재구축하지 않는다. 다만 나머지 라이프사이클이 기대하는 구조화된 형식으로 문서화할 뿐이다.

그 결과물은 처음부터 이 방법론을 통해 기능을 구축했을 경우 `/ai-dlc:elaborate`가 생성했을 아티팩트와 정확히 동일한 형태다. 모든 Unit에는 완료 기준이 있다. 모든 기준은 추적 가능한 증거 — 특정 테스트 파일, CI 검사, 배포 구성 — 를 참조한다. 모든 아티팩트는 `status: completed`로 표시되는데, 구축 단계가 없기 때문이다. 코드는 존재한다. 작업은 완료되었다. 부재했던 것은 구조뿐이었다.

## 7단계 워크플로

Adopt는 각 경계마다 대화형 확인 게이트를 두고 7단계를 거쳐 진행된다.

**1단계: 수집(Gather).** 사용자가 기능을 설명한다 — 무엇을 하는지, 코드가 어디에 있는지, 운영상 무엇이 중요한지. 이것은 양식 작성이 아닌 대화다. 시스템은 어디를 살펴봐야 할지 파악하기 위한 충분한 맥락이 필요하다.

**2단계: 탐색(Explore).** 5개의 병렬 서브에이전트가 코드베이스 전반에 걸쳐 각자 다른 차원에서 기능을 분석한다.

| 탐색기 | 분석 대상 |
|---|---|
| 코드 경로 | 진입점, 모듈 경계, 의존성 그래프, 아키텍처 패턴 |
| Git 이력 | 커밋 패턴, 작성자, 변화 타임라인, 리팩터링 이력 |
| 테스트 스위트 | 테스트 파일, 커버리지 패턴, 어서션 전략, 검증된 엣지 케이스 |
| CI 구성 | 빌드 단계, 테스트 명령, 품질 게이트, 배포 트리거 |
| 배포 표면 | 인프라, 환경 구성, 런타임 의존성, 관측 가능성 |

이들은 동시에 실행된다. 이 병렬성은 형식적인 것이 아니다 — 각 탐색기는 단일 분석 관점에 집중하여 독립적인 컨텍스트에서 동작하며, 이후 단계에서 종합될 결과물을 생성한다. 순차적으로 실행하면 아무런 이점 없이 실제 소요 시간만 배가될 뿐이다.

**3단계: 제안(Propose).** 시스템이 탐색기 결과를 종합하여 분해된 Unit을 포함한 Intent 초안을 제안한다. 사용자는 제안된 구조를 검토한다 — Unit 경계가 합리적인가? 분해 방식이 팀이 기능을 이해하는 방식과 일치하는가? 이것이 첫 번째 확인 게이트다.

**4단계: 기준(Criteria).** 성공 기준이 테스트 스위트와 CI 구성으로부터 역공학된다. 각 기준은 구체적인 증거를 가리킨다: "인증이 만료된 토큰을 거부한다"는 `test/auth/token_expiry_test.ts`를 참조한다. "속도 제한이 사용자별 할당량을 적용한다"는 `test/middleware/rate_limit_test.ts`와 부하 테스트를 실행하는 CI 단계를 참조한다. 기준은 발명되는 것이 아니라 — 코드베이스가 스스로에 대해 이미 증명하고 있는 것으로부터 추출된다. 사용자가 검토하고 승인한다.

**5단계: 운영 계획(Operational plan).** 시스템이 배포 표면 분석에서 도출된 모니터링, 인시던트 대응, 확장 고려사항, 유지보수 패턴을 포함하는 운영 계획을 생성한다. 사용자가 검토하고 승인한다.

**6단계: 작성(Write).** 아티팩트가 표준 형식으로 `.ai-dlc/{slug}/`에 기록된다. Intent 파일, Unit 파일, 디스커버리 노트, 운영 계획. 모든 Unit은 완료 상태로 표시된다.

**7단계: 인계(Handoff).** 시스템이 생성된 내용을 확인하고 이제 무엇이 가능한지 설명한다. 도입된 기능은 일급 시민이 된다.

## 완료 상태가 중요한 이유

Adopt가 생성하는 모든 아티팩트는 `status: completed`다. 이것은 기술적인 세부사항이 아니라 핵심 설계 결정이다.

Adopt는 작업을 만들지 않는다. 이미 완료된 작업 주위에 구조를 만든다. Adopt가 `status: active` 상태의 Unit을 생성한다면, 실행 루프가 그것을 구축하려 할 것이다. 구축할 것이 없다. 코드는 존재한다. 테스트는 통과한다. 완료 상태를 설정하는 것은 나머지 방법론에 이렇게 알리는 것이다: 이 기능은 실재하고, 문서화되었으며, 운영 준비가 되어 있다.

이것이 바로 Adopt를 도입하게 된 두 가지 기능을 가능하게 한다. `/ai-dlc:operate auth-system`이 동작하는 것은 Intent가 존재하고, 운영 계획이 존재하며, 상태가 기능이 라이브 상태임을 나타내기 때문이다. `/ai-dlc:followup auth-system`이 동작하는 것은 반복할 완료된 Intent가 존재하기 때문이다 — 시스템은 무엇이 구축되었는지, 기준이 무엇이었는지, 어떤 증거가 그것을 뒷받침하는지 알고 있다.

## 그린필드 도구에서 전체 라이프사이클로

Adopt는 AI-DLC를 새로운 작업만 다루는 방법론에서 소프트웨어 시스템의 전체 라이프사이클을 아우르는 방법론으로 변모시킨다. 새로운 기능은 `/elaborate`를 통해 진입한다. 기존 기능은 `/adopt`를 통해 진입한다. 둘 다 동일한 아티팩트 구조를 생성하고, 동일한 운영 워크플로에 참여하며, 동일한 반복 패턴을 지원한다.

이것이 중요한 이유는, 이미 존재하는 것을 설명할 수 없는 방법론은 실제 코드베이스와 만나는 순간 살아남지 못하기 때문이다. 팀은 제로에서 시작하지 않는다. 수년간 축적된 결정들, 출시된 기능들, 운영 지식에서 시작한다. 그 모든 것을 무시하는 라이프사이클 방법론은 장난감에 불과하다. 그것을 흡수하여 거버넌스 아래 가져올 수 있는 것이 진정한 도구다.

브라운필드 격차는 해소되었다. 어제 AI-DLC를 통해 구축되었든, 3년 전에 수작업으로 구축되었든 — 모든 기능이 전체 라이프사이클에 참여할 수 있다.
