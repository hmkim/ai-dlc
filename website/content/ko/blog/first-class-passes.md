소프트웨어 팀은 기능을 단 한 번의 Pass로 완성하지 않습니다. 디자이너는 목업을 만들고, 프로덕트 매니저는 동작 명세를 작성하며, 개발자는 코드를 구현합니다. 각 분야는 동일한 작업 단위를 서로 다른 시각으로 바라보며, 서로 다른 산출물을 만들고, 서로 다른 품질 기준을 적용하고, 서로 다른 질문을 던집니다.

AI-DLC는 이제 이 과정을 직접적으로 모델링합니다. Pass는 일급 개념입니다.

## 무엇이 부족했는가

AI-DLC에는 이미 스케줄링 개념으로서의 Pass가 존재했습니다. Intent 안에 `passes: [design, product, dev]`를 선언하면 DAG 스케줄러가 그에 따라 Unit을 순서대로 실행했습니다 — 디자인 태그가 붙은 Unit을 먼저 실행하고, 그다음 프로덕트, 그다음 개발 순으로 진행했습니다. 하지만 Pass가 하는 일은 스케줄링이 전부였습니다. 디자인 Pass의 빌더는 개발 Pass의 빌더와 동일하게 동작했습니다. 사용 가능한 워크플로도 같았고, 적용되는 지침도 같았습니다. 분야 레이블은 그저 형식적인 것에 불과했습니다.

그 결과, 디자인 Unit을 작업하는 에이전트는 와이어프레임 대신 프로덕션 코드를 생성했습니다. 프로덕트 Pass의 빌더는 동작 명세를 작성하는 대신 곧바로 구현으로 넘어갔습니다. 시스템은 각 Pass를 *언제* 실행할지는 알았지만, 각 Pass가 작업을 *어떻게* 형성해야 하는지는 알지 못했습니다.

## Pass의 새로운 동작 방식

Pass는 정의 파일입니다 — 프론트매터가 포함된 마크다운 파일로, 해당 Pass가 나타내는 분야, 사용 가능한 워크플로, 그리고 빌드 시 모든 hat에 주입되는 지침을 선언합니다.

세 가지 기본 제공 Pass는 다음과 같습니다:

**Design** Pass는 작업 범위를 시각 및 인터랙션 산출물로 제한합니다. 빌더는 와이어프레임, 목업, 디자인 토큰, 컴포넌트 명세를 생성합니다. 리뷰어는 기존 디자인 시스템과의 일관성, 접근성 기준, 반응형 동작을 검토합니다. 프로덕션 코드는 명시적으로 범위 밖입니다. `design` 워크플로만 사용 가능합니다.

**Product** Pass는 동작 명세 작성에 초점을 맞춥니다. 빌더는 인수 기준을 작성하고, 엣지 케이스를 식별하며, 데이터 계약과 상태 전환을 문서화합니다. 리뷰어는 명세가 추가 질문 없이 구현 가능할 만큼 충분히 명확한지 검증합니다. `default` 및 `bdd` 워크플로를 사용할 수 있습니다.

**Dev** Pass는 테스트 가능하고 배포 가능한 코드를 목표로 합니다. 빌더는 이전 Pass의 명세와 디자인 산출물을 기반으로 구현합니다. 리뷰어는 구현이 해당 산출물과 일치하는지, 그리고 모든 인수 기준에 통과하는 테스트가 존재하는지 검증합니다. `default`, `tdd`, `adversarial`, `bdd` 등 모든 표준 워크플로를 사용할 수 있습니다.

각 Pass는 해당 Unit에서 사용 가능한 워크플로를 제한합니다. 디자인 Unit은 `tdd` 워크플로를 사용할 수 없습니다 — 테스트 주도 개발은 목업에 적용되지 않기 때문입니다. 개발 Unit은 전체 워크플로 팔레트를 사용할 수 있습니다 — 구현 단계에서는 모든 워크플로가 유용하기 때문입니다. 이는 임의적인 제한이 아닙니다 — 시스템이 각 분야별 작업 방식에 대한 지식을 인코딩한 결과입니다.

## 재정의가 아닌 보강

Pass는 hats에도 동일하게 적용되는 보강 패턴을 따릅니다. 플러그인의 기본 제공 정의는 표준입니다 — 항상 로드되며 절대 교체되지 않습니다. 프로젝트가 동일한 이름의 Pass 또는 hat을 정의하면, 해당 지침은 플러그인 정의에 *추가*됩니다. 새로운 이름은 완전히 새로운 커스텀 항목을 생성합니다.

이 방식이 중요한 이유는 프로젝트가 실수로 방법론을 망가뜨리는 것을 방지하기 때문입니다. 프로젝트는 디자인 Pass에 "모든 목업에 Figma 컴포넌트 라이브러리를 사용하라"는 지침을 추가하면서도, 와이어프레임 생성 및 접근성 검토에 관한 Pass의 핵심 지침을 그대로 유지할 수 있습니다. 기본 제공 지침은 상한선이 아닌 하한선입니다.

동일한 패턴이 hats에도 적용됩니다. 프로젝트의 `builder.md`는 플러그인의 빌더를 교체하는 것이 아니라, 프로젝트별 컨텍스트로 확장합니다. 이는 이전 해석 패턴에서 의도적으로 벗어난 것입니다 — 이전에는 프로젝트 hat이 플러그인 hat을 완전히 재정의할 수 있었고, 프로젝트 정의에서 중요한 가드레일이 누락될 경우 예측 불가능한 동작이 발생했습니다.

## Pass 루프

정교화 단계에서 시스템은 설정된 Pass를 제안으로 제시합니다. 사용자는 Intent별로 이를 확인하거나, 순서를 변경하거나, 재정의할 수 있습니다. 단일 Pass 개발 전용 방식이 기본값으로 유지됩니다 — 멀티 Pass는 옵트인 방식입니다. 대부분의 작업에는 세 가지 분야별 반복이 필요하지 않기 때문입니다.

실행 중에는 활성 Pass의 모든 Unit이 완료되면 시스템이 사용자에게 알리고 멈춥니다. 이는 의도적인 경계입니다. Pass 간 전환에는 종종 인간의 판단이 필요합니다: 디자인 산출물이 실제로 필요한 내용을 담고 있는가? 동작 명세가 충분히 명확한가? 시스템이 자동으로 다음 단계로 넘어가지 않는 이유는, 분야 간 전환이 가장 중요한 결정이 이루어지는 지점이기 때문입니다.

Pass 되돌리기도 가능합니다. 개발 과정에서 디자인이 특정 인터랙션 상태를 누락했음이 드러나면, 작업을 디자인 Pass로 되돌릴 수 있습니다. Pass 루프는 일방통행 컨베이어가 아닙니다 — 실제 팀이 자연스럽게 수행하는 반복적 개선을 지원하는 피드백 사이클입니다.

## 커스텀 Pass

세 가지 기본 제공 Pass는 닫힌 집합이 아닙니다. 프로젝트는 `.ai-dlc/passes/` 디렉터리에 정의 파일을 추가하여 커스텀 Pass를 정의할 수 있습니다. 보안 중심 팀은 위협 모델링과 침투 테스트에 집중하는 `security` Pass를 추가할 수 있습니다. 데이터 팀은 계측 및 지표 검증에 초점을 맞춘 `analytics` Pass를 추가할 수 있습니다. Pass 시스템이 확장 가능한 이유는 분야가 보편적이지 않기 때문입니다.

커스텀 Pass는 사용 가능한 워크플로와 기본 워크플로를 직접 선언하며, 기본 제공 Pass와 마찬가지로 지침이 hats에 주입됩니다. 설정 스키마는 `default_passes`에 임의의 문자열을 허용합니다 — 유지 관리가 필요한 하드코딩된 열거형이 없습니다.

## 이것이 중요한 이유

Pass는 hats만으로는 표현할 수 없는 개념을 인코딩합니다: *동일한 역할*이 어떤 분야가 작업을 주도하느냐에 따라 다르게 동작해야 한다는 생각입니다. 빌더는 언제나 빌더이지만, 와이어프레임을 만드는 빌더와 통합 테스트를 작성하는 빌더는 다르게 생각합니다. 디자인 일관성을 검토하는 리뷰어는 테스트 커버리지를 검토하는 리뷰어와 다른 기준을 적용합니다.

Pass가 없으면 두 가지 실패 패턴 중 하나가 발생합니다. 에이전트가 컨텍스트와 무관하게 개발 동작을 기본값으로 삼아 — 명세가 필요할 때 코드를 생성하고, 목업이 필요할 때 테스트를 작성하거나 — 아니면 Pass 시스템이 이제 자동으로 처리하는 내용을 수동으로 복제하기 위해 점점 더 구체적인 Unit 설명을 작성하는 방식으로 보완하게 됩니다.

Pass는 소프트웨어 구축이 각자의 기준, 산출물, 워크플로를 가진 여러 분야를 포함한다는 사실을 시스템이 이해하는 방식입니다. 에이전트는 단순히 *무엇을* 만들어야 하는지만 아는 것이 아닙니다. 각 단계에서 *어떻게 생각해야 하는지*를 압니다.
