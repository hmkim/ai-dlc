오늘 출시된 두 가지 기능은 서로 다른 각도에서 동일한 근본적인 문제를 다룹니다: AI 에이전트는 잊어버린다는 것입니다.

에이전트는 여러분의 디자인 시스템이 어떻게 생겼는지 잊어버립니다. 어떤 컴포넌트 라이브러리를 사용하는지 잊어버립니다. 팀이 4px가 아닌 8px 간격을 선택했다는 것도 잊어버립니다. 새로운 Intent는 매번 백지 상태에서 시작하고, 에이전트는 이미 내려진 결정들을 다시 발견하거나 재발명합니다.

지식 합성은 에이전트에게 구축의 기반이 될 프로젝트 스냅샷을 제공합니다. 디자인 프로바이더는 에이전트에게 손을 쥐어줍니다.

## 기억 상실 문제

AI-DLC의 구성 루프는 작업을 Intent와 Unit으로 분해하며, 각각은 명확한 완료 기준을 가진 집중된 컨텍스트 윈도우 내에서 실행됩니다. 이 구조는 핵심적인 역할을 합니다 — 대규모 작업 전반에 걸쳐 모델이 일관성을 잃는 것을 방지합니다. 그러나 동시에 새로운 Intent가 매번 새롭게 시작된다는 것을 의미합니다. 지난주에 인증 플로우를 구축한 에이전트와 오늘 대시보드를 구축하는 에이전트는 그 사이에 일어난 일에 대한 기억을 전혀 공유하지 않습니다.

실질적인 결과는 복합적으로 나타납니다. 디자인 토큰이 약간씩 다른 값으로 재발명됩니다. 컴포넌트 패턴이 기능마다 달라집니다. API 관례가 흔들립니다. 코드베이스는 공유 문서 없이 교체되는 팀이 구축한 프로젝트의 특징을 갖게 됩니다 — 실제로 그것이 바로 현실이기 때문입니다.

## 지식 합성

`/ai-dlc:knowledge-synthesize` 스킬은 이 문제를 직접적으로 해결합니다. 이 스킬은 정교화 단계에서 코드베이스를 스캔하고 구조화된 지식 아티팩트를 추출합니다 — CSS 및 테마 파일에서 디자인 토큰, UI 레이어에서 컴포넌트 사용 패턴, 기존 화면에서 레이아웃 원칙, 그리고 추론 가능한 경우 결정의 근거까지 추출합니다.

이 스킬은 다섯 가지 아티팩트 유형을 생성합니다: 디자인, 아키텍처, 제품, 관례, 도메인. 각 아티팩트는 `.ai-dlc/knowledge/`에 기록되며 Intent 전반에 걸쳐 유지됩니다. designer hat이 시작될 때 무언가를 생성하기 전에 디자인 지식을 로드합니다. builder hat이 시작될 때 기술 패턴을 로드합니다. reviewer hat이 결과물을 평가할 때 확립된 관례에 따라 검증합니다.

이 스킬은 코드베이스 스캔입니다 — 기존 파일을 읽고, 패턴을 추출하며, 구조화된 스냅샷을 작성합니다. 두 곳에서 실행됩니다: 정교화 단계(새 Intent를 시작할 때)와 통합 이후(Intent가 완료되고 모든 Unit이 병합된 후). 통합 후 갱신이 그린필드 프로젝트의 루프를 닫는 역할을 합니다. Intent 1이 기반을 구축합니다 — 디자인 토큰, 컴포넌트 라이브러리, 아키텍처. 통합 Pass 이후 합성이 병합된 코드베이스에서 다시 실행되어 해당 패턴을 지식 아티팩트로 캡처합니다. Intent 2는 정교화를 시작할 때 빈 스캐폴드 대신 실제 지식을 발견하고, Intent 1이 확립한 것 위에 구축합니다.

지식에는 유효 기간이 있습니다. 각 아티팩트는 `last_updated` 타임스탬프를 가지며, hats는 90일이 지난 지식을 잠재적으로 오래된 것으로 취급합니다. 지식에 `--color-primary: #3B82F6`이라고 기록되어 있지만 실제 코드베이스가 `#2563EB`로 변경된 경우, 에이전트는 오래된 기록을 맹목적으로 따르는 대신 불일치를 표시합니다. 지식은 결정에 정보를 제공하지만 오늘 코드가 실제로 말하는 것을 재정의하지는 않습니다.

이 스킬은 성숙도를 인식합니다. 그린필드 프로젝트는 빈 섹션이 있는 스캐폴드 아티팩트를 받습니다 — 스캔할 것이 없기 때문입니다. 초기 프로젝트는 낮은 신뢰도 결과를 가진 얕은 스캔을 받습니다. 성숙한 프로젝트는 완전한 처리를 받습니다: 패턴당 5~10개의 대표 파일에 걸친 심층 스캔, 다운스트림 hats가 신뢰할 수 있는 높은 신뢰도 아티팩트.

## 일급 디자인 프로바이더

지식 합성은 기억 문제를 해결합니다. 디자인 프로바이더는 도구 문제를 해결합니다.

이전에는 AI-DLC와 디자인의 관계가 간접적이었습니다. 디자인은 폴더 안의 스크린샷으로 존재했습니다. 에이전트는 비전을 통해 분석하고, 스펙을 추출하고, 그 스펙을 기반으로 구축했습니다. 디자인 도구 자체 — Figma, Canva, 팀이 사용하는 무엇이든 — 는 워크플로우 외부에 있었습니다. 에이전트가 와이어프레임을 생성해야 할 때는 HTML을 생성했습니다. 구축된 결과물을 디자인과 비교해야 할 때는 스크린샷을 비교했습니다.

AI-DLC는 이제 여섯 가지 디자인 도구와 네이티브로 통합됩니다: **Canva**, **Figma**, **OpenPencil**, **Pencil.dev**, **Penpot**, **Excalidraw**. 각각은 도구별 MCP 작업을 통합된 인터페이스에 매핑하는 기능 기반 프로바이더 추상화를 통해 지원됩니다.

통합은 워크플로우의 세 단계에 걸쳐 이루어집니다:

**정교화.** Intent를 Unit으로 분해할 때, 와이어프레임 생성 스킬은 이제 팀의 디자인 도구에서 직접 와이어프레임을 생성할 수 있습니다. Canva가 구성된 경우 Canva 디자인을 생성합니다. OpenPencil이 사용 가능한 경우 `.op` 파일을 생성합니다. HTML 와이어프레임은 프로바이더가 구성되지 않은 경우의 폴백으로 유지됩니다 — 기존 동작은 완전히 보존됩니다.

**디자인.** designer hat은 시작 시 활성 프로바이더를 발견하고, 디자인 토큰(도구 자체 시스템의 브랜드 색상, 폰트, 간격)을 로드하며, 네이티브 디자인 아티팩트를 생성합니다. 각 Unit의 프론트매터에 있는 `design_ref` 필드는 프로바이더 네이티브 아티팩트를 가리킵니다 — `canva://design/abc123` URI, `.ai-dlc/{intent}/designs/unit-01-login.op` 파일 경로, 또는 Figma 파일 참조. 에이전트는 도구를 우회하는 것이 아니라 도구 안에서 작업합니다.

**리뷰.** reviewer hat은 시각적 비교를 위해 `design_ref` 값을 PNG 내보내기로 변환합니다. 변환 시스템은 통합된 파이프라인을 통해 프로바이더 URI, 로컬 네이티브 파일, 클라우드 전용 참조를 처리합니다. 프로바이더 네이티브 디자인이 존재하는 경우, 시각적 충실도 게이트는 HTML 와이어프레임보다 더 높은 일치도를 기대합니다 — 참조 품질이 더 높으므로 기준도 그에 맞게 높아집니다.

### 자동 감지

디자인 프로바이더가 `auto`(기본값)로 설정된 경우, AI-DLC는 현재 세션에서 사용 가능한 디자인 MCP 도구를 감지하고 우선순위에 따라 최적의 프로바이더를 선택합니다. Canva MCP가 연결된 팀은 자동으로 Canva 통합을 받습니다. OpenPencil이 있는 팀은 OpenPencil을 받습니다. 별도의 구성이 필요하지 않습니다 — 특정 도구를 고정하려는 팀을 위한 명시적 구성도 지원됩니다.

### 우아한 성능 저하

이것이 가장 중요한 설계 원칙입니다: 프로바이더 없이도 아무것도 중단되지 않습니다. designer hat, 와이어프레임 스킬, 시각적 리뷰 파이프라인을 통한 모든 경로에는 이전과 동일하게 작동하는 폴백이 있습니다. HTML 와이어프레임. 스크린샷 기반 분석. 텍스트 디자인 스펙. 프로바이더 통합은 완전히 기능하는 기준선 위에 기능을 추가합니다.

팀은 준비가 되었을 때 디자인 프로바이더를 도입합니다. 하네스는 이를 강요하지 않습니다.

## 두 기능이 함께 작동하는 방식

두 기능은 상호 보완적입니다. 지식 합성은 코드베이스에서 디자인 토큰을 추출합니다. 디자인 프로바이더는 도구에서 디자인 토큰을 로드합니다. 둘 다 존재하는 경우 프로바이더 토큰이 우선합니다 — 도구는 디자인 시스템의 현재 상태에 대한 권위 있는 소스이며, 지식 아티팩트는 시스템이 그렇게 설계된 방법과 이유에 대한 더 넓은 맥락을 캡처합니다.

구체적인 예시: 디자인 지식 아티팩트에는 기본 색상이 `#3B82F6`이며 흰색 배경에서 WCAG AA 대비 준수를 위해 선택되었다고 기록되어 있습니다. Canva 브랜드 키트는 `#2563EB`를 반환합니다 — 디자인 팀이 지난주에 업데이트했습니다. designer hat은 `#2563EB`(프로바이더의 현재 값)를 사용하고 지식 아티팩트와의 불일치를 기록하며, 이후 갱신될 수 있습니다.

지식은 근거를 제공합니다. 프로바이더는 현재 상태를 제공합니다. 함께, 에이전트에게 조직적 기억과 실시간 정확성을 모두 부여합니다.

## 팀에게 의미하는 것

지원되는 디자인 도구를 이미 사용하는 팀에게, 디자인 프로바이더 통합은 그들이 일하는 곳에서 만납니다. 디자이너는 Canva, Figma, 또는 Penpot을 계속 사용합니다. AI 에이전트는 동일한 도구에서 동일한 브랜드 키트와 디자인 토큰을 사용하여 디자인을 생성하고 읽습니다. 내보내기-스크린샷-가져오기 루프가 없습니다. 하네스는 도구의 네이티브 언어를 구사합니다.

시간이 지남에 따라 여러 기능을 구축하는 팀에게, 지식 합성은 각 새로운 Intent가 에이전트가 모든 것을 처음부터 다시 발견하는 대신 오늘 존재하는 프로젝트의 구조화된 스냅샷 — 디자인 토큰, 컴포넌트 패턴, 도메인 용어, 아키텍처 관례 — 으로 시작한다는 것을 의미합니다. 통합 후 갱신은 이 스냅샷을 자동으로 최신 상태로 유지합니다: 완료된 모든 Intent가 재합성을 트리거하므로 지식은 항상 최신 병합 상태를 반영합니다.

두 기능 모두 하네스를 더 조용하게 만듭니다. 덜 재발견합니다. 덜 재발명합니다. 덜 표류합니다. 에이전트는 프로젝트가 어떻게 생겼는지 파악하는 데가 아니라 실제 작업에 컨텍스트 예산을 씁니다.
